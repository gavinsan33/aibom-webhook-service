# Implementation Notes

This file holds the detailed rationale and edge-case behavior behind the mechanics summarized in `README.md`. Read the README first for the high-level picture; this is the "why" and the fine print.

## Pod Matching and Injection

Pods are matched if they are owned directly by a Job or PyTorchJob, **or** if any container requests `nvidia.com/gpu` resources. JobSet pods match through their child Jobs. `JobSet` and `RayJob` are also in the mutator's owner-kind set (`matchedOwnerKinds`), but neither ever owns a pod directly — KubeRay pods are owned by a `RayCluster` — so Ray pods are only matched through a GPU request (#105). When GPU resources are present, the webhook mirrors the pod's **total** GPU allocation — the sum of each container's effective claim (limit if set, else request), i.e. exactly what the scheduler places the pod against — onto the discovery init container so `nvidia-smi` runs against every GPU the pod actually gets (mirroring only the first container's claim, as before, would under-report `gpu_count`/`gpu_models` on multi-container pods). The claim has to be a real `nvidia.com/gpu` resource rather than a dcgm-exporter-style privileged container with host `/dev` mounts: the `nvidia-smi` binary and the NVML driver library it links against are not part of any base image (verified against the CUDA runtime images the discovery image is built from — they ship libcuda's compat layer, not the driver), and on standard device-plugin setups the NVIDIA Container Toolkit injects both from the node's driver only because the claim's Allocate response sets `NVIDIA_VISIBLE_DEVICES` on the container. Mirroring costs the pod no extra GPUs for scheduling: a pod's per-resource requirement is max(sum of containers, max of init containers), and init containers never run concurrently with the app containers. Both injected containers (discovery init container and dataset sidecar) also declare explicit, small cpu/memory requests **and** limits: a namespace's `LimitRange` backfills whatever a container leaves unset (`default`/`defaultRequest`), so without this an arbitrary workload namespace (e.g. defaults 2 CPU/8Gi, default requests 1 CPU/2Gi) would stamp its defaults onto a container that needs ~100Mi, inflating the pod's scheduling footprint (init containers count toward a pod request as max(sum of containers, max of init containers)). The discovery container's cpu limit is a whole core deliberately — its single-threaded CPU/memory benchmarks are meant to characterize the node, and any cgroup cpu quota below 1 core would throttle them into reporting container-limited numbers. The webhook always fails open (`failurePolicy: Ignore`) — if the service is down, pods are created normally.

Fail-open also hides a *network* failure: admission requests come from the API server (host network, or a konnectivity tunnel on hosted control planes), not from a pod in the install namespace. A namespace-isolating NetworkPolicy (e.g. a platform-provisioned "allow ingress only from this namespace") drops them, and the result is indistinguishable from "pod didn't qualify" — no error, no log line on the webhook (a no-mutation response isn't logged either), and workloads run uninstrumented with no AIBOM. Diagnosed on a real cluster this way: the pod had no `aibom.io/instrumented` label, the webhook log had no entry for it, a pod in *another namespace* timed out reaching the service while one in the same namespace got a 405, and a server-side dry run of a bare GPU pod came back unmutated. `charts/aibom-webhook/templates/networkpolicy.yaml` (`aibom-webhook-admission`, `networkPolicy.enabled`, default on) allows ingress to the webhook pod's container port 8443 (not the Service's 443) with no `from`, since the API server's source address varies by cluster. It's additive, so it can't restrict anything. It was applied by hand under a different name first (`allow-aibom-webhook-admission`); delete that one once the chart is deployed.

**Webhook RBAC (#148).** The `aibom-webhook` ClusterRole is read-only: `list`/`watch` on pods, jobs and namespaces for the informers. Every write the webhook makes (data ConfigMaps, the per-job ServiceAccount/Role/RoleBinding/token Secret, `serviceaccounts/token`, pod and Job finalizer patches, the failure Event) comes from the `aibom-webhook` Role in `charts/aibom-workload-namespace`'s `webhook-access.yaml`, bound to the webhook's ServiceAccount in each opted-in namespace. (Postprocess Jobs and signing keys are in the webhook's own namespace, where the webhook chart's `postprocess.yaml` gives it a Role for them.) A namespace labeled `aibom.io/enabled` that never installed that chart gets Forbidden errors instead of working partially. The per-job Role must stay within what that Role grants (Kubernetes' escalation check), which `TestWorkloadNamespaceRoleCoversPerJobRole` enforces. The token Secret is create-only (`ensureTokenSecret`): a namespaced get/update can't be scoped to a per-job name and would also expose the signing keys, so a second pod of the same job mints a token it then discards. This narrows the blast radius to opted-in namespaces; the webhook can still run a pod as any ServiceAccount in them.

For long-running pods with no Job owner (e.g. KServe `InferenceService` predictor pods, owned by a ReplicaSet and never "complete"), the watcher triggers on the pod's deletion via a separate pod-level finalizer instead of Job completion.

Matching never consults an `aibom.io/instrumented` value already present on the incoming pod — only owner kind and GPU resource requests, neither of which a requester can spoof away. The `MutatingWebhookConfiguration` only matches `CREATE` with `reinvocationPolicy: Never`, so there's no legitimate scenario where this label is already `"true"` on a fresh admission; trusting it would let a workload dodge instrumentation entirely just by pre-setting the label the webhook itself would otherwise add. For the same reason, a pod that doesn't qualify has any workload-supplied `aibom.io/instrumented`/`aibom.io/instrumented-by` stripped rather than left in place — otherwise the watcher's `aibom.io/instrumented=true` selector could be tricked into compiling an AIBOM for a workload that was never actually instrumented.

Dataset detection (`runtime_detector.py`, running as `sitecustomize.py` inside the user's own application container) only ever writes its results to a local file on the shared `aibom-data` volume (`$AIBOM_DATASET_OUTPUT`) — it does not import `k8s_api` or talk to the Kubernetes API at all. The `aibom-dataset-sidecar` container (see Dataset Data Signing below) reads that file and performs the actual ConfigMap write from outside the app container's control. Dataset detector's `k8s_api` import is wrapped in a soft `try/except ImportError` — since it runs inside the user's own application container, a missing/stale mount degrades to "no dataset detection" instead of crashing the user's training process at Python startup.

How the hooks get installed (#106):

- **`sitecustomize`, not `usercustomize`.** Python skips `usercustomize` whenever the user site directory is disabled: in any venv without system site-packages (`/opt/venv`, uv-built images), under `PYTHONNOUSERSITE` or `-s`, and when uid ≠ euid. `sitecustomize` is still imported in all of those. Because `/aibom-hooks` is on `PYTHONPATH` ahead of site-packages, the detector shadows any `sitecustomize.py` the image ships (Debian/Ubuntu's, a conda env's, a platform team's), so `_run_shadowed_sitecustomize` finds the next one on `sys.path` and runs it. Errors in it are reported the way `site.py` reports them and don't stop startup. Interpreters started with `-I`, `-E` (both ignore `PYTHONPATH`) or `-S` (no `site` at all) still get no hooks.
- **`PYTHONPATH` injection shapes (#103).** `buildDatasetDetectorPatches` adds `PYTHONPATH=/aibom-hooks` when the container spec has none, prepends to a literal `value`, and for a `valueFrom` entry appends a second `PYTHONPATH=/aibom-hooks:$(PYTHONPATH)` entry (Kubernetes expands `$(VAR)` against earlier entries and the later duplicate wins) instead of emitting an invalid `replace` on a `value` member that doesn't exist. `AIBOM_DEBUG` is no longer injected; workloads set it themselves. A `PYTHONPATH` set by the *image* (`ENV PYTHONPATH=/app`) is invisible at admission and would be overridden by the injected value, so the workload declares it with the `aibom.io/python-path` pod annotation (e.g. `/app:/app/lib`), which is appended behind `/aibom-hooks` when the spec has no `PYTHONPATH` of its own. Without the annotation the override still happens; there is no automatic detection.
- **Post-import hook on `sys.meta_path`.** `_PostImportHookFinder` asks the other finders for each framework's real spec and wraps that loader's `exec_module` on the instance (the loader's type is unchanged), so the hook is installed the moment the module finishes executing, before the import statement that loaded it binds anything. The previous `builtins.__import__` wrapper only installed hooks once the import stack unwound to depth 0, so a module that was itself being imported and did `from datasets import load_dataset` at its top level (a user helper, or trl's own CLI) kept the unpatched function. It also didn't see `importlib.import_module`, and its depth counter was shared across threads. A hook is marked installed only after the attributes it patches resolve, so a failed lookup isn't recorded as installed.
- **`TrainingArguments.__post_init__`, not `__init__`.** `TrainingArguments` and its subclasses (trl's `SFTConfig`/`DPOConfig`, `Seq2SeqTrainingArguments`) are dataclasses, each with its own generated `__init__` that never calls the parent's, so the old `__init__` hook only caught the base class. Every generated `__init__` calls `__post_init__`, and subclasses that override it call `super().__post_init__()`.

### `aibom.io/postprocess-for` Trust Boundary

`aibom.io/postprocess-for` marks a Job (and its pod template) as one the watcher itself created for postprocessing a triggering workload (see Postprocess Flow below) — `isPostprocessPod` (`mutator.go`) checks it to avoid re-instrumenting a postprocess Job's own pod, and `onJobEvent` (`watcher.go`) checks the Job-level value to avoid postprocessing a postprocess Job a second time. Like `aibom.io/instrumented`, this is just Pod/Job metadata a requester can set on their own manifest — unlike that label, though, it can't simply be ignored, since the watcher's real postprocess Jobs legitimately carry it and must still be recognized.

The `MutatingWebhookConfiguration` intercepts `batch/v1` `Job` creation (in addition to pods) specifically to check this: `SanitizeJobPostprocessLabel` (`jobguard.go`) strips the label from both the Job's own labels and its pod template's labels whenever `request.userInfo.username` doesn't match `--trusted-watcher-identity` (set at deploy time to this Deployment's own ServiceAccount, `system:serviceaccount:<namespace>:aibom-webhook` — the watcher runs in the same binary/identity, so this is exactly what a watcher-created Job's admission request carries). `request.userInfo` is populated by the API server from real authentication and can't be spoofed the way labels can, so this is what actually closes the gap rather than just raising the bar. Left unconfigured, the check is disabled entirely (fails open) rather than stripping a value with nothing to compare against.

`isPostprocessPod` additionally requires a plain `batch/v1` `Job` owner reference before honoring the label at all — real postprocess pods are always Job-owned, so a raw Pod submitted directly (never wrapped in a Job) can't be one. On its own this is defense-in-depth, not a full close: Kubernetes doesn't validate that a submitted object's `ownerReferences` point to anything real, so a requester who fabricates a Job-kind owner reference on their own raw Pod alongside the label could still get through undetected by either check above (since no Job was ever created for the Job-admission check to see).

`--trusted-job-controller-identity` (`Mutator.TrustedJobControllerIdentity`, `values.yaml`'s `webhook.trustedJobControllerIdentity`) closes that remaining gap when configured: it compares this pod admission's own `request.userInfo.username` against the cluster's built-in Job controller identity (commonly `system:serviceaccount:kube-system:job-controller`) — a fabricated `ownerReferences` entry can't also make Kubernetes report the wrong requester, since that value comes from real authentication on the request, not anything the submitted object controls. It's opt-in and empty by default rather than defaulted to that common value, because the exact identity string depends on the cluster's `kube-controller-manager --use-service-account-credentials` setting and isn't guaranteed identical across every distro — a wrong guess would misclassify real postprocess pods, not just spoofed ones, so operators need to verify it against their own cluster first. Left unconfigured, only the weaker ownerReference-only check applies.

### Runtime Detection Output Durability (#107)

`runtime_detector.py` runs in every Python process of every instrumented container (each torchrun rank, spawned DataLoader worker, the launcher, `pip`), and all of them write one shared file, `$AIBOM_DATASET_OUTPUT`, which the dataset sidecar polls and publishes. Writing it once at `atexit` with an unlocked read-merge-write lost data two ways.

- **Concurrent writers.** `_flush` takes an exclusive `flock` on `<output>.lock` (bounded wait, so a stuck holder can't hang process exit) around read → `_merge_output` → write to `<output>.<pid>.tmp` → `os.replace`. Writers take turns, and the sidecar and the next writer only ever see a complete file. Before this, 8 concurrent flushers lost entries in most trials and occasionally left invalid JSON, which made the sidecar's final pass skip the file and publish nothing.
- **Nothing flushed before exit.** `atexit` is skipped by SIGKILL (OOM, the kubelet's grace-period kill), by SIGTERM under Python's default handler, and by `os._exit`. Changes now schedule a debounced flush (`AIBOM_FLUSH_DEBOUNCE_S`, default 2 s, one daemon `Timer` per burst) from `_record`, the DataLoader in-place merge, and `_runtime_info` (a dict subclass that notifies, only when a value actually changes — `_flush` re-captures argv-derived values into it every run, and notifying on identical writes would reschedule forever). The notification is inert until hooks are installed. That is the real protection against SIGKILL: whatever was detected more than ~2 s earlier is already on disk. A SIGTERM handler, installed only if the handler was `SIG_DFL` at startup, flushes and then restores `SIG_DFL` and re-delivers the signal, so the process still dies by SIGTERM (exit status 143) rather than exiting cleanly. An application's own handler (uvicorn, torchrun) is left alone; it exits through the interpreter, so `atexit` runs. In the signal path `_flush` takes `_lock` with a timeout and skips the 10 s `git status`, since the signal may have interrupted the thread holding the lock.
- **Fork.** `os.register_at_fork(after_in_child=...)` gives a forked child fresh locks and no pending timer; it would otherwise inherit a lock held by a thread (the flush timer) that doesn't exist in the child, and a `Timer` that will never fire.

**Stale values from unrelated processes.** `_runtime_info` merges used to only add or overwrite keys, so `pip install` running in a checkout on `main` followed by `train.py` in a detached-HEAD clone labelled the clone's commit `branch=main`. Two changes: git provenance is captured only by a process that already detected something of its own (checked before the git capture, after the argv/accelerate captures), so `pip` and launcher shims no longer write it; and the `git_*` keys are treated as one observation, so a process that captures any of them replaces the whole group in the file. The watcher's `mergeDatasets` does the same across pods: the `git_*` group comes from the first pod that reported any of it, and `datasets` entries are deduped by the same identity fields the detector uses (see Dataset Declaration and Reconciliation), so N JobSet pods loading one dataset give one entry. Other `runtime_info` keys are still first-pod-wins per key, with pods ordered by completion index and then newest attempt first (#114), not by list order.

**Sidecar final publish.** The shutdown pass (`_publish_final`) retries a failed `patch_configmap` up to 4 times with backoff (1 s, doubling) instead of dropping the last flush; the periodic pass already retried by not advancing its mtime.

**Limits.** SIGKILL still loses whatever was detected in the last debounce window, and anything captured only at exit (git dirty state, argv/accelerate values that appear late). A PID 1 that doesn't forward SIGTERM (a `sh -c` wrapper, as in the FSDP example) never delivers it to the Python process, so only the debounced flush protects those runs. Only runtime-hook data is affected by any of this: model/training CLI flags, hardware, storage identity, pod termination status and telemetry come from other sources (CLI parsing, the discovery init container, the watcher, Prometheus), which is why an AIBOM from a killed run can still look complete. For a vLLM predictor, uvicorn handles SIGTERM and exits through the interpreter, and there is little for the hooks to record anyway.

### Stale Finalizers (#104)

The watcher adds `aibom.io/log-extraction` (Jobs) and `aibom.io/log-extraction-pod` (bare/KServe pods) so it gets a chance to build the AIBOM at deletion time, and removes them afterward. The webhook also puts `aibom.io/log-extraction-pod` on every Job-owned pod at admission (see Job Pods Held Until Postprocessed below). Two ways nothing was left to remove them, leaving the object `Terminating` forever and hanging its namespace's deletion:

- **Namespace opted out.** `onJobEvent`/`onPodEvent` returned early when `aibom.io/enabled` wasn't `"true"`, before any removal path. They now check `isNamespaceOptedOut` first and release our own finalizer (skipping the postprocess, not the cleanup). Deleting the object produces an update event, so a stuck object is released the next time it's touched. `isNamespaceOptedOut` is deliberately not `!isNamespaceEnabled`: it requires the namespace to be found in the informer cache with the label absent or not `"true"`, since a transient cache miss must not strip finalizers from a still-enabled namespace and lose its AIBOM. A namespace that is being deleted also counts as opted out. Its AIBOM would be created in it and deleted with it, and the namespace's RoleBinding (the webhook's only grant to patch pods and Jobs there, see Webhook RBAC) has no finalizer, so it's usually gone first and a later finalizer removal is Forbidden, leaving the namespace stuck `Terminating`. Releasing on the first event shrinks that window but doesn't close it.
- **Chart uninstalled.** `templates/finalizer-cleanup-hook.yaml` is a `post-delete` hook that runs the webhook image with `--strip-finalizers` (`watcher.StripAllFinalizers`): a cluster-wide, unfiltered list of Jobs and Pods, dropping only our two finalizers and leaving others (patched with the object's `resourceVersion`, retried on conflict, idempotent so a hook retry is safe). `post-delete` rather than `pre-delete`, because while the Deployment still exists the watcher can re-add a finalizer to a Job it sees after the strip. The release's own ServiceAccount and ClusterRole are gone by then, so the hook carries its own (cluster-wide `list`/`get`/`patch` on `jobs` and `pods`, nothing else) and deletes them on success; on failure they stay for debugging, and `before-hook-creation` clears them next time. Toggle with `finalizerCleanup.enabled`; `helm uninstall --no-hooks` skips it.

Not covered: `kubectl delete` of the Deployment without `helm uninstall` (no hook runs), and the case where the installing identity can't create ClusterRoles (disable the hook and strip finalizers by hand with the `--strip-finalizers` image).

### Job Pods Held Until Postprocessed (#164)

A Job that hits `activeDeadlineSeconds` (or a `podFailurePolicy` `FailJob` rule) has its pods deleted by the Job controller itself, before the `Failed` condition is set. The Job finalizer doesn't help: it only holds the Job, and it's the Job's deletion that it protects, not its pods'. So the watcher used to find no pods, `shouldPostprocess` returned false, and no AIBOM was made.

The mutator now adds `aibom.io/log-extraction-pod` (`aibomdata.PodFinalizerName`) at admission to any pod with a `batch.kubernetes.io/job-name` label, the same label the watcher routes Job pods by. Adding it at admission rather than from the watcher means there's no window before a fast deadline. `onJobEvent` releases it (`finishJob` → `releaseJobPods`) on every Path B outcome except a retry: after the postprocess Job is created, when the Job doesn't qualify, on give-up after `maxPostprocessRetries`, on a resync of an already-postprocessed Job (which is what retries a failed release), and for a Job deleted while running that never qualified. The pod informer now covers Job pods too (selector `aibom.io/instrumented=true`, no longer `!batch.kubernetes.io/job-name`) so `releaseJobPods` reads the cache rather than listing per resync. Pods are matched by the Job's UID (`batch.kubernetes.io/controller-uid`) as well as its name, so an earlier run's Job being cleaned up doesn't release a same-named rerun's pods. `onPodEvent` still leaves Job pods to the Job path, with two exceptions: an opted-out namespace releases them (as for bare pods), and so does a deleted pod whose Job is gone from the cache (`--cascade=orphan`) or has been replaced by a same-named Job with a different UID, since nothing else would. `removePodFinalizer` patches at the cached pod's `resourceVersion` because the Job controller removes its own `batch.kubernetes.io/job-tracking` finalizer from the same pods at about the same time, and a merge patch from a stale copy would put it back. A conflict is retried on the next event or resync rather than by re-reading, since the webhook's Role has `patch` but no `get` on pods.

Trade-offs: a pod deleted while its Job is still running (suspension, Kueue preemption, eviction) stays `Terminating` in a terminal phase until the Job finishes or is deleted. Its containers have stopped, so it holds no node resources, and it's included in the AIBOM like any other attempt. Pods also stay `Terminating` while the watcher is down, as bare pods already did. JobSet siblings are released by their own Job's event, not by the triggering Job's postprocess, so sibling pods read for `containers.json` may already be gone, as before. On Kubernetes versions where the Job controller sets `Failed` as soon as it deletes the pods, rather than once they've stopped (the cluster in #164 waited ~7 s), the watcher can read them mid-shutdown: container status still unset (`status` `null`) and the dataset sidecar's final publish not yet in the data ConfigMap.

### Discovery Init Container Fails Open (#104)

`aibom-discovery` gates the workload's own containers (an init container must exit 0 before they start), so a crash or hang in it would fail or stall a user's Job because of instrumentation. Three layers keep that from happening. (1) The mutator runs `python3 /scripts/generate_snapshot.py || echo ... >&2`, so a script that can't even start (no `python3` in `--discovery-image`, exit 127) is logged and the init container still exits 0. (2) Inside the script every stage that touches something the workload or image controls runs through `_run_stage`: the InferenceService lookup, the model-file read, the ConfigMap name lookup and the ConfigMap write. An exception becomes a warning plus a fallback and the rest of the snapshot is still written. (3) Each stage runs under a `SIGALRM` deadline (60 s), which is the only thing that can interrupt a blocking syscall. `_read_small_file` also checks `os.path.isfile` first, since `open()` on a FIFO named `README.md` on the model PVC blocks until a writer appears; `isfile` follows symlinks, so a link to a FIFO or device is skipped too.

Not covered: the init container being killed (OOM, node loss) or `/bin/bash` missing from the discovery image, since layer 1 is itself a bash command.

### Discovery Data Signing

`discovery-<pod-name>.json` (hardware/GPU data) and `storage-<pod-name>.json` (KServe `InferenceService` storage identity, see Model Auto-Detection below) — both written by the `aibom-discovery` init container — are HMAC-SHA256 signed before being written to the data ConfigMap, using a per-namespace key (`aibom-discovery-hmac-key` Secret, created by `charts/aibom-workload-namespace`'s `signing.yaml`) mounted **only** into the discovery init container — never into an application container (see `mutator.go`'s `buildDiscoverySigningKeyVolume`). Both keys share the same signing key and verification path (`generate_snapshot.py`'s `sign_payload`, `watcher.go`'s `verifySignature`) since both are produced by that same trusted process. The watcher reads the same Secret — via a namespaced `Role`/`RoleBinding` (also in `signing.yaml`, scoped by `resourceNames` to that exact name) granted per-namespace to the webhook's ServiceAccount, not a cluster-wide `ClusterRole`, so this identity's read access is limited to namespaces that installed `aibom-workload-namespace`, not a same-named Secret anywhere on the cluster — and verifies the signature before merging a pod's discovery or storage data into the aggregate `discovery.json`/`storage.json` a postprocess Job reads; an entry with a missing or invalid signature is dropped and logged, not silently accepted.

This closes both the overwrite race (#29) and first-write forgery for hardware claims and storage identity: since the app container never has the key, it cannot produce a validly-signed write no matter what RBAC it holds on the ConfigMap itself. That holds against code running inside the workload's containers, not against whoever writes the pod spec: any pod can mount any Secret in its own namespace with no RBAC check, so a user who can create pods in an enabled namespace can mount this key (or the dataset key below) and forge data that verifies (#149). This can't be closed while the signers run in the workload's pod: denying pods that mount these Secrets would still leave `shareProcessNamespace` and ephemeral debug containers to reach the sidecar's key, and dataset data is forgeable without any key through the handoff file (the self-attestation problem under Dataset Data Signing). Only data gathered outside the pod, such as hardware from node labels, would hold against pod authors. Only the compiled-AIBOM key is out of reach, since it lives in the webhook's namespace (see Compiled AIBOM Signing). `docs/reference/signing.md` states this for users.

Where a field *can* be sourced from outside the pod cheaply, it now is — not to close the signing gap (that stays as documented), but for accuracy and robustness (#110/#115). `environment.gpu_count` is taken from the pod's own `nvidia.com/gpu` claim (summed across containers) rather than the init container's `nvidia-smi | wc -l`: the watcher records each container's effective claim as `gpu_limit` in `containers.json` (`buildPostprocessInputs`), and `compile_aibom` sums it per pod (`pod_gpu_count`), both in the environment section and in the telemetry GPU-skip gate, falling back to the discovery value only when no container claims a GPU. `environment.gpu_type`/`gpu_memory_mb` prefer DCGM's `DCGM_FI_DEV_FB_TOTAL` (its `modelName` label and the device framebuffer, keyed on `exported_pod`) via `_dcgm_gpu_hardware`, a best-effort instant query needing no RBAC beyond the `cluster-monitoring-view` the postprocess Job already holds; it falls back to the in-pod `nvidia-smi` values when DCGM isn't present. The remaining `environment` fields (`cpu_model`, `numa_nodes`, `cuda_version`, `driver_version`, `kernel_version`) and the KServe storage identity have no out-of-pod source without new node/`serving.kserve.io` RBAC, so they stay discovery-sourced; granting the always-on watcher that cluster-wide read was judged not worth it for a non-security artifact (see #149's close), leaving those as the known residual of the same self-attestation limitation.

A symmetric key (HMAC), not an asymmetric keypair, is used deliberately: the discovery init container's image is admin-configurable (`--discovery-image`; the chart defaults to the project's minimal UBI image, `discovery/Dockerfile`, but any image with `python3`, `bash`, `lscpu` and `lsblk` can be set), not guaranteed to have a crypto library installed, so signing had to stay within Python's stdlib (`hmac`/`hashlib`). Since the verifier (the watcher, a project-controlled component) is equally trusted, an asymmetric split (which exists specifically to let an *untrusted* party verify without being able to forge) buys nothing extra here.

A missing Secret (a namespace whose `aibom-workload-namespace` chart install predates `signing.yaml`) is treated as "verification unavailable," not as tampering — discovery data passes through unverified rather than being dropped, so this rolls out gradually across existing namespaces rather than breaking them until they're upgraded. Verification is also skipped (data passes through unverified, with a logged warning) when the Secret read fails for any other reason — e.g. Forbidden or a transient API error — and when the Secret exists but lacks its key field (`fetchDiscoverySigningKey`/`fetchDatasetSigningKey` in `watcher.go`); see #115.

### Dataset Data Signing

`dataset-<pod-name>.json` is signed too, but by a different component than discovery/storage data, using a separate key (`aibom-dataset-hmac-key`, its own Secret in `signing.yaml`) — not because the mechanics differ, but because *who's trusted to produce it* differs. `runtime_detector.py`'s in-process hooks (`datasets.load_dataset`, `DataLoader`, etc.) run inside the user's own application container, which this project's threat model treats as untrusted; handing that same container a signing key — even a dataset-specific one — would prove nothing, since the process capable of forging the underlying claim would also be the process signing it.

Instead, `dataset_sidecar.py` runs as a **Kubernetes native sidecar** (an init container with `restartPolicy: Always`, GA since Kubernetes 1.29): it starts without blocking the main containers on it completing, runs for the pod's entire lifetime, and — critically — is only terminated *after* every main container has already exited. It polls the same local file `runtime_detector.py` already wrote unconditionally, and on change, signs and publishes it to the ConfigMap using its own credentials (shared with the discovery init container's per-job identity, see RBAC-scoping below) — the app container itself holds no Kubernetes API credentials for this purpose at all anymore (#47). The dataset-signing key is mounted only into this sidecar, never the app container or the discovery init container, and kept separate from the discovery/storage key deliberately: the sidecar and the discovery init container are different processes with different inputs, so a compromise of one shouldn't need to also invalidate trust in data signed by the other.

**Shutdown race (SIGTERM during startup).** The sidecar is PID 1 in its container, and the kernel drops a signal that has no handler for PID 1 instead of applying its default action. `dataset_sidecar.py` therefore installs its SIGTERM handler before `import k8s_api` and the module-level setup, not in `main()`. When a pod's main containers exit within a few seconds of the sidecar starting (a 2 s Job), the kubelet's SIGTERM used to arrive while Python was still importing and was lost: the sidecar ran out the 30 s grace period and was killed (exit 137, shown as `Init:Error`), and its final publish was skipped. Found with the startup benchmark's 2 s Jobs; a 10 s main container was already fine.

**This closes the ConfigMap-forgery vector, not the deeper self-attestation problem.** The underlying content still originates entirely from `runtime_detector.py`'s in-process hooks — a compromised or malicious training script can still fabricate what it reports *at the source* (e.g. monkeypatching the hook, or writing directly to the local handoff file in the expected shape). The sidecar can only vouch for "this is exactly what appeared in the handoff file," not that the file's content reflects what genuinely happened during training. Closing that gap would require observing dataset access from somewhere the app process doesn't control at all — e.g. eBPF-based observation of actual file/network activity from the kernel — which is tracked as a distinct follow-up (#47's issue comments), not solved here.

### Compiled AIBOM Signing

The compiled AIBOM custom resource itself (`spec.data`, the final JSON `postprocess.py` produces) is signed too (#27), but with an asymmetric Ed25519 keypair rather than the HMAC used above — a deliberate inversion of the discovery/dataset reasoning. There, signer and verifier (the discovery init container/dataset sidecar, and the watcher) are equally trusted, project-controlled processes, so a shared HMAC key buys nothing an asymmetric split wouldn't also give. Here, the intended verifiers include parties genuinely outside that trust boundary — `oc-aibom`, or anything reading an AIBOM independently archived outside the cluster with no reason to trust wherever it came from. Handing every such verifier the same key used to sign would let any of them forge a signature too, so the private key is mounted read-only into the `aibom-postprocess` Job only. It's one Secret per workload namespace, `aibom-compiled-signing-key-<namespace>`, in the **webhook's own namespace** — generated by the watcher on first use (`ensureCompiledSigningKey`, stdlib Ed25519 + PKCS8 PEM) rather than by the workload-namespace chart. It can't live in the workload namespace: any pod there can mount a Secret from its own namespace with no RBAC check, and could then sign a forged AIBOM (#149). For the same reason the postprocess Job itself runs in the webhook namespace as that namespace's `aibom-postprocess` ServiceAccount, which a workload pod can't run as. The ServiceAccount has no API grant on any Secret: the kubelet mounts the key.

`sign_aibom` (`postprocess.py`) signs `spec.data` canonicalized per **RFC 8785 (JSON Canonicalization Scheme, JCS)** — deliberately not the hand-rolled `sort_keys=True, separators=(",", ":")` convention `generate_snapshot.py`'s `sign_payload` uses for discovery/storage data. That convention works there because signer and verifier are both this same Python codebase; here the intended verifier (`oc-aibom`) is written in Go, and Python's `json.dumps` and Go's `encoding/json` don't format floats or escape non-ASCII strings identically by default — a hand-rolled convention would make the signature spuriously fail to verify for perfectly legitimate AIBOMs the moment a float or a unicode string showed up. JCS exists specifically to solve "two independent implementations need to agree on canonical bytes for the same logical JSON value," which is exactly this problem; the Python side uses the `rfc8785` package, the Go side (`oc-aibom`) uses `gowebpki/jcs` (same reference lineage). Cross-checked directly against each other on representative AIBOM-shaped fixtures (floats, unicode, nested/empty collections) before this was wired up — see `test_sign_aibom_matches_go_jcs_reference_output`, which pins a byte string actually produced by the Go implementation, so a future `rfc8785` upgrade that drifted from the spec would be caught here.

Signing happens over `spec.data`, before `create_custom_object` — the CRD's `spec` is CEL-immutable (`self == oldSelf`), so the signature has to be baked in at creation time; there's no later "sign after the fact" step, and no in-cluster tampering vector for the watcher or anyone else to guard against post-creation (the CRD already closes that). `spec.signature` and `spec.signaturePublicKey` are stored as sibling fields alongside `spec.data`, not embedded inside it — mirroring how `discovery-<pod>.json`'s signature lives in a separate `.sig` ConfigMap key rather than inside the signed JSON itself, avoiding a self-referential payload, and avoiding duplicating `data`'s full content a second time just to sidestep a formatting mismatch that JCS already solves. Embedding the public key directly in the CR (rather than requiring a separate lookup) makes an independently archived copy self-contained and verifiable with zero cluster access; `postprocess.py` also idempotently publishes it to a plain (non-secret) `aibom-compiled-signing-public-key` ConfigMap via `k8s_api.patch_configmap`'s existing create-or-merge semantics, giving a cluster-side anchor to cross-check an archived copy's embedded key against, for anyone who doesn't want to simply trust whatever key a given exported document claims for itself.

If the watcher can't create the key (it logs a warning), the Secret volume is optional, so the AIBOM is still created, just without `spec.signature`/`spec.signaturePublicKey`, rather than failing the Job.

Since `postprocess.py`'s own container image (`postprocess/Dockerfile`) is fully project-controlled — unlike the discovery init container's admin-configurable image — it can afford real dependencies (`cryptography`, `rfc8785`) for this, unlike `generate_snapshot.py`'s stdlib-only constraint that ruled out asymmetric crypto and cross-language canonicalization there in the first place.

**Scope and known limitations.** The signature covers `spec.data` only — the sibling `spec.jobName`/`modelName`/`experimentIntent`/`collectedAt` fields (all derived from `data` at creation time, kept as separate fields only for `additionalPrinterColumns`/quick filtering) are not themselves signed. Not exploitable today (only the trusted `aibom-postprocess` ServiceAccount can create an AIBOM at all), but a verifier should re-derive anything security-relevant from the signed `data` rather than trusting those sibling fields directly. Key rotation isn't handled either: regenerating `aibom-compiled-signing-key` overwrites `aibom-compiled-signing-public-key` with the new key, so AIBOMs signed under a since-rotated-out key lose their live-cluster cross-check anchor (they still carry their own embedded `signaturePublicKey`, which is exactly the un-anchored trust the ConfigMap exists to avoid) — the same unresolved gap the HMAC keys above already have, not something this feature was expected to solve first.

JCS's number canonicalization (RFC 8785 §3.2.2.3, an ECMA-262-derived algorithm) is only defined for values representable as an IEEE 754 double without losing integer precision beyond 2^53 — `rfc8785` raises `IntegerDomainError`/`FloatDomainError` rather than silently producing a wrong-but-plausible byte string for anything outside that range or a NaN/Infinity. `sign_aibom`'s caller wraps the whole call in a broad `except Exception`, so this degrades to "AIBOM created unsigned" rather than failing the Job — but it means an AIBOM containing an out-of-range number silently loses signing entirely rather than surfacing why. Not expected in practice given what `compile_aibom()` actually populates (percentages, byte counts, rates, timestamps-as-strings), but worth knowing if a future field introduces very large integers (e.g. a raw byte count in the petabyte range as an `int` rather than a formatted string).

`oc-aibom` implements the verifier side of this (`internal/aibom.Verify`, surfaced as a `Signature:` line in `oc aibom describe`): it canonicalizes the AIBOM's `spec.data` as a generic decoded map (not its own typed `Data` struct, which wouldn't reproduce the exact JSON that was signed) via `gowebpki/jcs`, then checks that against `spec.signature` under `spec.signaturePublicKey`, and separately cross-checks that embedded key against the live `aibom-compiled-signing-public-key` ConfigMap before reporting anything as fully verified — a signature that only matches its own embedded key proves nothing, since a forger controlling `data` could just as easily generate their own keypair and embed that. This also closes out the "not verified against a real cluster's own JSON handling" caveat noted in earlier drafts of this section: JCS's numeric canonicalization is defined purely in terms of the resulting IEEE 754 double, so a value Kubernetes' unstructured decoder happens to type as `int64` vs. `float64` canonicalizes identically either way as long as the numeric value itself round-trips exactly — confirmed by both sides independently producing byte-identical output for the same fixture (`test_sign_aibom_matches_go_jcs_reference_output` here, `TestCanonicalizeData_MatchesGoJCSReferenceOutput` in `oc-aibom`).

## Postprocess Flow (detail)

1. **Data ConfigMap read/merge**: The Job's pods (and sibling pods in a JobSet) have already written their own discovery/storage data (via the `aibom-discovery` init container) and dataset data (via the `aibom-dataset-sidecar` container, see Dataset Data Signing above) into the per-workload data ConfigMap (`{job-name}-aibom-postprocess-data`, in the workload's namespace) via the Kubernetes API. The watcher reads that ConfigMap, verifies the signatures, and writes the aggregated `discovery.json`/`dataset.json`/`storage.json` plus `annotations.json`/`containers.json` that `postprocess.py` expects into a separate inputs ConfigMap in the **webhook's namespace**, named after the postprocess Job (`aibomdata.PostprocessInputsConfigMapName`). The workload's own ConfigMap is deleted when the postprocess Job finishes.
2. **Finalizer removal**: If the Job has the `aibom.io/log-extraction` finalizer, it is removed after this step, allowing Kubernetes to complete the deletion. (The finalizer's name predates the current data path but is kept as-is to avoid breaking finalizers already held on live objects.)
3. **Postprocess Job**: Runs `postprocess.py` in the webhook's namespace, under that namespace's `aibom-postprocess` ServiceAccount. The Job is named `<workload>-<hash>-aibom-postprocess` (`aibomdata.PostprocessJobName`, a hash of namespace/workload, so same-named workloads in different namespaces and long names don't collide, #130) and labeled `aibom.io/postprocess-for` and `aibom.io/postprocess-namespace`. Its access to the workload's namespace comes from the `aibom-postprocess` Role in `aibom-workload-namespace`'s `rbac.yaml`, bound to that ServiceAccount cross-namespace: `aiboms.aibom.io` create/get, `aibomtelemetries` create/patch and `aiboms/finalizers` update for the telemetry time-series object (see Telemetry Time Series), and create/patch of the public-key ConfigMap only. The Job's `AIBOM_JOB_NAMESPACE` is the workload's namespace, which is what its Prometheus queries filter on. It loads discovery/dataset data from the ConfigMap mount, optionally queries Prometheus for telemetry, compiles everything into an AIBOM JSON document, and creates the `AIBOM` custom resource directly via the Kubernetes API (no watcher involvement) — a failed create exits the process non-zero, so Kubernetes' own Job retry handling (`backoffLimit`) retries it.
4. **Cleanup**: Once the postprocess Job finishes (success or failure — `isJobFinished` treats both as terminal), it's annotated `aibom.io/aibom-collected` and the per-job workload identity is removed either way. A **succeeded** Job is deleted along with its data ConfigMap, so a same-named rerun of the workload doesn't collide with leftovers. A **failed** one is kept (#112): its pod logs (`oc logs -n <webhook-ns> job/<job>`, a command the watcher logs) are the only record of why no AIBOM was made, and its data ConfigMap is the input needed to retry by hand. Every postprocess Job is created with `ttlSecondsAfterFinished` (`failedPostprocessTTLSeconds`, 24 h) and its data ConfigMap is given an `ownerReference` to it, so Kubernetes' TTL controller removes both after a day instead of leaking them. If the same workload name is postprocessed again inside that window, `existingPostprocessJob` deletes the failed leftover first (only one that finished `Failed`) — otherwise the new Job's create would hit `AlreadyExists` and silently produce no AIBOM.

**Same-named reruns.** The data ConfigMap, the per-job identity and the postprocess Job are all named after the workload, so a rerun that starts while the previous run is still being postprocessed (telemetry retries alone take a couple of minutes) shares all three. Each postprocess Job records its trigger's kind and UID (`aibom.io/postprocess-trigger-kind`/`-uid`), and two checks use them. `collectAIBOM` skips deleting the data ConfigMap and identity when `triggerReplaced` finds a same-named Job (or bare pod) with a different UID in the informer cache: the rerun's pods are already writing into that ConfigMap with that identity, and deleting them lost the rerun's discovery data (so no GPU count and no telemetry at all) and its sidecar's credentials. The rerun's own collection cleans them up; the old run's pod keys left in the ConfigMap are ignored, since data is read by pod name. And when the rerun finishes while the earlier postprocess Job is still running, `existingPostprocessJob` returns `errPostprocessBusy` before the inputs are built (building them would overwrite the inputs ConfigMap the running Job mounts); `onJobEvent`/`onPodEvent` keep the finalizer and retry on the next resync without counting it against `maxPostprocessRetries`. The same applies when a JobSet recreates a child Job that was deleted while the JobSet was still active (the serving examples' client deletes the server Job), which is a different UID under the same name. Such a replacement owns none of the original's pods, which are still terminating and match its name selector, so `getInstrumentedPods` drops pods whose controlling Job has a different UID; a replacement that never ran a pod then doesn't qualify, and isn't postprocessed into a duplicate of the original's AIBOM. The cache can lag a replacement created in the moment before the check; its pods won't have written anything yet. Postprocess Jobs created before these annotations existed are treated as belonging to the current run, as before. The only Event emitted is an `AIBOMPostprocessFailed` Warning on the workload Job naming the failed postprocess Job, since the workload's owner can't read the webhook namespace (the webhook's per-namespace Role grants `events` create). `--debug-keep-postprocess-jobs` (`debug.keepPostprocessJobs` chart value) skips this — the Job is still annotated `aibom.io/aibom-collected` so a resync doesn't try to collect it again, but it and its data ConfigMap are left in place for inspecting postprocess pod logs/exit state or the ConfigMap's merged discovery/dataset data. Leaks one of each per completed workload indefinitely; not for routine production use.

### Workload Selection and Grouping

**Which jobs get postprocessed?** A job in an `aibom.io/enabled` namespace qualifies if any of its pods request `nvidia.com/gpu` resources (limits or requests > 0), or the job has any `aibom.io/*` annotations. Internal labels (`aibom.io/instrumented`, `aibom.io/postprocess-job`) are excluded from this check. Jobs that are themselves postprocess jobs (labeled `aibom.io/postprocess-for`) are always skipped.

**When does postprocessing trigger?** When the Job finishes (`JobComplete` **or** `JobFailed` condition — `isJobFinished` treats both as terminal, so failed workloads get an AIBOM too, including one whose pods the Job controller deleted on a deadline; see Job Pods Held Until Postprocessed), or on Job deletion (`DeletionTimestamp` set — the finalizer path, used for JobSet server pods killed rather than completing naturally). Each job is postprocessed at most once; after the postprocess job is created, the original job is annotated `aibom.io/postprocess-job` and subsequent events are skipped.

**How are workloads grouped?** Each qualifying job gets its own postprocess job — no cross-job merging. If a job belongs to a **JobSet** (`jobset.sigs.k8s.io/jobset-name` label), its postprocess job lists the sibling pods across the whole JobSet (so their `containers.json` entries — image, status, limits — are included), and inherits sibling `aibom.io/*` annotations if the triggering job has none. Sibling *discovery/dataset* data is **not** currently included: each sibling pod writes to its own child Job's data ConfigMap, while `buildPostprocessInputs` reads only the triggering Job's (#105). Example: in a vLLM server + client JobSet, only the server job qualifies (GPU + annotations); the client job is skipped, and the server's AIBOM lists the client pods but carries no hardware/dataset data for them.

**Which pods get postprocessed?** Bare pods with no Job owner (no `batch.kubernetes.io/job-name` label — e.g. a KServe predictor pod owned by a ReplicaSet) are postprocessed via a separate path: same qualifying criteria as Jobs, but read directly from the pod (GPU resources on its containers, or `aibom.io/*` annotations — KServe propagates `spec.predictor.annotations` down onto the pod). Only pods already carrying `aibom.io/instrumented=true` are candidates. There's no "complete" state for a long-running pod, so postprocessing triggers purely on deletion via a distinct pod-level finalizer (`aibom.io/log-extraction-pod`), and there's no JobSet-style sibling merging here — each qualifying pod gets its own postprocess Job.

### Pod Termination Status

`execution_metadata.pods[].status`/`.exit_code` (e.g. `"OOMKilled"`/`137`, `"Completed"`/`0`) come from the live Pod object the watcher already reads in `buildPostprocessInputs` when building `containers.json` — specifically `ContainerStatuses[].State.Terminated.Reason`/`.ExitCode` — not from anything the discovery init container or app process reported at pod startup. This is a deliberate split: a pod's `pod_metadata` (name, start time, etc.) is known the moment the discovery init container runs, but how the pod eventually died is only knowable afterward, from the watcher's own read of the Pod API at postprocess time — the one point in this pipeline positioned after the fact.

A pod with multiple containers reduces to one status the same way `kubectl get pods` does: `OOMKilled` wins over any other reason even if only one container in the pod hit it (the more actionable signal), then any other non-zero exit, then `"Completed"` once every container that reported a status exited cleanly. `execution_metadata.status` further rolls this up across every pod in the workload (all of a JobSet's sibling pods, not just the triggering one) the same way — one sibling OOMing surfaces at the job level even if the rest completed normally. **Retried Jobs (#112).** `restartPolicy: Never` + `backoffLimit` makes a new pod per attempt, and all of them are in `containers.json`. The watcher tags each container with `job_result` — the terminal condition (`Complete`/`Failed`) of the Job that owns its pod, read from the Job object it already holds (the triggering Job, plus JobSet siblings from the list it already makes; the ClusterRole has no `get` on jobs). In `compile_aibom`, a pod whose Job is `Complete` but whose own status isn't `Completed` is an earlier attempt: it keeps its own `status`/`exit_code` in `pods[]` with `retried_attempt: true`, and is left out of `execution_metadata.status`. A Job that is `Complete` with no usable pod status reports `Completed`; a `Failed` Job whose pods all report clean exits reports `Failed`. The watcher also records a `Failed` condition's reason as `job_failure_reason`, and a Job that failed with `DeadlineExceeded` reports `DeadlineExceeded` unless a pod was `OOMKilled`, since its pods' own statuses (`Error`, exit 143) only describe the kill (#164). Like the other rollups this spans a JobSet's siblings: one sibling hitting its deadline makes the workload `DeadlineExceeded`, even if another reported a genuine `Error`. For a `Failed` Job every attempt still counts, so `OOMKilled` anywhere wins as before. Bare pods and Jobs that hadn't finished (being deleted) have no `job_result` and roll up as before.

**llm-d role (#167).** llm-d labels each model-server pod `llm-d.ai/role` (`prefill`, `decode` or `encode`), and each of those pods gets its own AIBOM. The watcher copies the label into `containers.json` as `serving_role`, `compile_aibom` puts it on `pods[].serving_role`, and `inference.serving_role` is set when every pod with a role agrees, so a prefill pod's throughput and latency aren't read as a whole deployment's. Combining prefill and decode pods into one AIBOM is out of scope: they're owned by separate Deployments or LeaderWorkerSets and postprocessed one pod at a time.

**Restarts in place (#112).** With `restartPolicy: OnFailure` the same pod restarts its container, so a kill is only in `lastState`. The watcher also captures `RestartCount` and `LastTerminationState.Terminated` as `restart_count`/`last_terminated_reason`/`last_exit_code`, which land on `pods[]` as `restart_count`/`last_termination_reason`/`last_exit_code` (omitted if nothing restarted; `OOMKilled` preferred across containers, restarts summed). This is detail only: `status` stays the pod's final outcome, so an OOM followed by a clean restart still reads `Completed`, with the kill visible beside it.

A pod with no container status captured at all (the watcher couldn't read Pod status, or — on the bare-pod finalizer path — the pod hadn't actually stopped) reports `status`/`exit_code` as `null` rather than a guessed value.

This only identifies *that* and *how* a container was killed — it says nothing about *why* memory usage grew to that point (that's `resource_utilization.metrics.gpu_memory_used`/`memory_usage`'s job, and telemetry can still come back empty if it raced ingestion lag or the OOM happened before Prometheus scraped anything). Signing doesn't apply here the way it does to discovery/storage data (see Discovery Data Signing above): this is read directly from the Kubernetes API by the watcher itself, a trusted process, not written by anything running inside the workload's own container.

## Model Auto-Detection

Model/training config is auto-populated through three complementary detection layers:

- **CLI-arg parsing** (`postprocess.py`): parses each container's command/args to auto-populate model, fine-tuning, and inference fields without requiring annotations. Detection is command-based, so it also sees into `sh -c "... && trl sft ..."`-style wrapper scripts (common when a job needs to `pip install` before running its training CLI) by shell-splitting the script and scanning tokens the same way as a plain `command: [...]` list. Tools recognized: **vLLM**, **TGI**, **SGLang**, **LMDeploy** (serving) and **trl** (fine-tuning). **llm-d** runs vLLM as its engine, so its model-server pods are detected (and their telemetry collected) as vLLM.
- **Runtime object hooks** (`runtime_detector.py`): catches scripts that build config directly in Python instead of via CLI flags — `transformers.TrainingArguments`, `transformers.PreTrainedModel.from_pretrained` (model name, architecture, dtype, quantization config), and `peft.LoraConfig` (LoRA rank/alpha, adaptation method). This covers plain `transformers.Trainer` scripts with no recognizable CLI shape. Fixes from #109:
  - **First model load wins.** Only a process's first `from_pretrained` is recorded, so a DPO reference model, reward model or distillation teacher loaded later doesn't replace the trained model's name, architecture, dtype, `device_map` or quantization. The slot is claimed when the call starts, so a load nested inside another one's `from_pretrained` can't win over its caller, and released if the load raises. A teacher or reward model loaded *before* the trained one is still misreported; recording every load with a role would fix that.
  - **Mixed precision is a separate field.** `TrainingArguments`' `bf16`/`fp16` is written as `mixed_precision` (→ `training.mixed_precision`), not `dtype`, which is the weights' dtype from `from_pretrained`.
  - **QLoRA is resolved in `postprocess.py`.** The peft hook only records `lora`/`dora`/`rslora`, and `postprocess.py` turns a runtime `lora` into `qlora` when the runtime hooks also saw quantization, so it no longer depends on whether `LoraConfig` was built before the model loaded.
  - **Storage details follow the detected model.** An `aibom.io/model-name` that differs from the detected name drops the storage-derived `revision`/`base_model`/`size_bytes`.
- **KServe InferenceService storage path** (`detect_model_from_storage` in `postprocess.py`): for a KServe `InferenceService` backed by an S3/MinIO data-connection bucket (`spec.predictor.model.storage.key`/`path`, the ODH/RHOAI convention), the predictor's built-in vLLM container always runs with a fixed `--model=/mnt/models` mount — no CLI arg identifies the actual model, since that only exists on the `InferenceService` object. Only applies to predictors already instrumented via the GPU-request fallback; a GPU-less predictor still isn't instrumented at all.

  Resolution happens inside the **`aibom-discovery` init container itself** (`generate_snapshot.py`'s `resolve_inference_service_storage`), at pod startup — not from the watcher, and not lazily at pod deletion. Reasoning: deleting the InferenceService is the normal way one of these pods gets deleted, and Kubernetes' garbage collector removes the InferenceService object from etcd well before the delete cascades to the pod — a lookup at deletion time would 404 almost every time, for exactly the trigger this exists to detect. Resolving at pod startup instead means the InferenceService that caused this pod to exist is essentially guaranteed to still be there.

  The init container knows its InferenceService's name via a downward-API env var (`INFERENCESERVICE_NAME`, only injected for pods already carrying that label — a downward API reference to a nonexistent label fails admission outright, so this can't be added unconditionally for every workload kind), does a single `GET` using the **workload's own namespace-scoped RBAC** (`aibom-workload-inferenceservices` Role, mirroring `aibom-workload-data`), and writes the result into the shared data ConfigMap as `storage-<pod-name>.json`. The always-on webhook/watcher process has no `serving.kserve.io` RBAC at all.

  **This is identification, not verification.** `model.name` is just the final path segment of the declared storage location (e.g. `models/tinyllama-1.1b-chat` → `tinyllama-1.1b-chat`) — nothing resolves the `storage.key` Secret or reads the bucket. A renamed or generically-named bucket path (`models/v2`, `models/final`) will be misreported, and there's no check that the bucket contents match the name. This also makes it storage-backend-agnostic — MinIO, AWS S3, or anything else KServe's storage-initializer supports — since only the `InferenceService`'s own declared string is read, never the endpoint it points to.

  **Pre-pulled models on a PVC (`pvc://` storageUri).** The folder name in the path is whatever someone chose (`qwen-32b`), so for these the discovery init container also reads the model's own metadata files (`generate_snapshot.py`'s `read_model_source_files`) into a `model_files` block in the same HMAC-signed `storage-<pod>.json`. `postprocess.py`'s `detect_model_from_storage` then prefers `model_files.repo_id` over the folder name and records which won in `model.name_declared_via` (`model_files_readme` or `storage_path`; `annotation` if `aibom.io/model-name` overrode it). Sources, all small files, never weights:

  - README.md front matter + H1 title → `repo_id` (Hugging Face `org/name`), `base_model`. `repo_id` is taken from `license_link` **only when its repo name matches the H1 title** — a fine-tune's `license_link` commonly points at its base model, and claiming that name would be wrong.
  - `.cache/huggingface/download/*.metadata` (written by `huggingface_hub`) → `revision`, the commit the snapshot was downloaded at.
  - `config.json` → `architecture`, `dtype`. These fill `model.architecture`/`model.dtype` only when no CLI `--dtype`/annotation already set them (`main()` does not let storage override them).
  - `model.safetensors.index.json` → `model.size_bytes`.

  The PVC reaches the init container via the webhook, not the pod's existing mounts: this webhook's configuration name (`aibom-webhook`) sorts before KServe's (`inferenceservice.serving.kserve.io`), so the pod has no `/mnt/models` mount yet at our admission. `modelSourcePVC` (`mutator.go`) instead parses KServe's `internal.serving.kserve.io/storage-initializer-sourceuri` pod annotation (`pvc://<claim>/<subpath>`; KServe-labeled pods only, `..` rejected) and adds its own read-only volume + `subPath` mount at `/mnt/aibom-model` on the init container alone (`AIBOM_MODEL_DIR`). **Still identification, not verification:** anyone with write access to the PVC can edit these files, and the HF etags/commit are never checked against the weights. S3/MinIO sources are unaffected (nothing to mount). Not read: `generation_config.json` sampling defaults and per-file weight hashes.

  **`hf://` and `oci://` storageUris.** `detect_model_from_storage` parses these schemes instead of taking the last path segment: `hf://org/model[:rev|@rev][/subpath]` yields `model.name = org/model` (any subpath is dropped) and `model.revision = rev` (`name_declared_via: hf_uri`); `oci://registry/repo[:tag]` yields the reference without the tag (`oci_uri`), with `model.revision` set to the digest from the matching container's `image_id` in `containers.json` when one exists. Still declared, not verified: an unpinned `hf://` is whatever `main` was at pull time. `gs://`/`https://`/`azure://` keep the generic last-segment behavior.

**How the CLI parser scopes what it reads (#108).** `_flatten_container_command` expands `sh`/`bash`/`zsh`/`dash -c` wrappers (any flag cluster containing `c`, after other flags: `bash -l -c`, `-euc`, `-xc`) and leaves the separators (`&&`, `||`, `;`, `|`, `&`, unquoted newlines) as their own tokens; `_split_segments` cuts on them. Each detector then looks only at the arguments of the one invocation it cares about, never the whole script. Scanning everything is what made `trl grpo --use_vllm` and `pip install trl[vllm]` look like a vLLM server (flipping `experiment_intent` to `inference`), read pip's `-q` as `--quantization`, and take `pip install deepspeed` for a launch.

- **vLLM**: an invocation is `vllm serve` or `-m vllm.entrypoints...api_server`. `vllm bench ...` is a client and ignored. The model can be positional (`vllm serve org/model`), but only directly after `serve` or after flags whose arity is known; `--model` wins when both appear. snake_case flags, `--flag=false` and `--no-flag` are understood. A `vllm serve` with no resolvable flags still reports `serving_engine`. For the `vllm/vllm-openai` image run with only `args` (its ENTRYPOINT is the server), `_detect_vllm_from_entrypoint_args` treats the args as vLLM's when `command` is unset; matching is by image name only. `_VLLM_IMAGE_RE` also matches llm-d's `llm-d-xpu`/`llm-d-cpu`/`llm-d-rocm` images, whose ENTRYPOINT is vLLM's api_server (#165). Not `llm-d-cuda`/`llm-d-aws`, whose ENTRYPOINT is NVIDIA's generic wrapper, so their pods spell out `vllm serve` (llm-d-modelservice's `vllmServe` mode) and match by command; and not the org's routing sidecar, scheduler, simulator or `llm-d-xpu-sglang` images. The routing sidecar is a native sidecar in llm-d's charts and recipes, so it isn't in `containers.json` anyway.
- **TGI / SGLang / LMDeploy** (`detect_tgi`/`detect_sglang`/`detect_lmdeploy_from_command`): same shape as the vLLM detector — find the server invocation (`text-generation-launcher ...`; `python -m sglang.launch_server ...`; `lmdeploy serve api_server ...`), parse the model and a few shared flags, emit `serving_engine` + `model_name` under vLLM's own key names so the model/inference sections and intent inference pick them up unchanged. LMDeploy's model is positional after `api_server`. Each flag map is intentionally small (model name is what matters most); engine-specific tuning flags beyond the shared ones (tensor-parallel, max-len, dtype, quantization, and each engine's own gpu-memory analogue — SGLang's `--mem-fraction-static` / LMDeploy's `--cache-max-entry-count` map onto vLLM's `gpu_memory_utilization`; LMDeploy's `--model-format` is its quantization flag) aren't exhaustively mapped. TGI's image sets `text-generation-launcher` as ENTRYPOINT, so `_detect_tgi_from_entrypoint_args` handles the args-only KServe case; SGLang/LMDeploy images expect an explicit command. Quantization is still inferred from the model name when no flag set it, same as vLLM.
- **trl**: an invocation is `trl <subcommand>` or `-m trl...`, outside package-manager segments (`pip`, `uv pip`, `conda`, ...). Bare booleans (`--use_peft --lora_r 16`) mean true; `--use_peft false`, `=false` and `--no_use_peft` mean false. Fractional epochs are kept as floats. `trl sft --config cfg.yaml` now reports `training_framework` (intent `training`), but the YAML is **not read** — it lives in the training container, which `postprocess.py` can't see — so model/dataset/LoRA settings set only there are still missed.
- **Axolotl / LLaMA-Factory** (`detect_axolotl_from_command`/`detect_llamafactory_from_command`): same shape as trl — find the training invocation (`axolotl train ...` or legacy `-m axolotl.cli.train`; `llamafactory-cli train ...`), emit `training_framework` + the model/LoRA/training fields under trl's own key names so the model/training/fine_tuning sections and intent inference pick them up unchanged. Axolotl's modern CLI is kebab-case and its legacy CLI snake_case; `_split_flag` normalizes both. Both tools are config-file driven and **those YAMLs aren't read** (same limit as `trl --config`) — Axolotl reports only the values passed as CLI overrides, LLaMA-Factory only those in flag mode; a pure config-file run still reports `training_framework` (and so an intent) with nothing else. Adapter resolution: Axolotl's `--adapter` (`qlora`, or `lora` + `--load-in-4bit`) and LLaMA-Factory's `--finetuning_type lora` (+ `--quantization_bit`/`--use_dora`/`--use_rslora`) map to `fine_tuning.adaptation_method`; LLaMA-Factory's `full`/`freeze` carry none (intent stays `training`). LLaMA-Factory's `--dataset` isn't parsed as the declared name (it's a comma-separated list keyed to `dataset_info.json`, and a bare `--dataset` would false-positive on serving bench clients) — runtime detection and annotations still apply.
- **Parallelization**: a launcher counts only as the command word of its own command (`torchrun`, `python -m torch.distributed.run`, ...). `torchrun --nproc_per_node=1` and `mpirun -np 1` aren't data parallel. `accelerate launch --use_fsdp`/`--use_deepspeed` and `--config_file <preset>.yaml` are recognized; `runtime_detector.py` also reads `--config_file` to resolve `distributed_type`.
- **Unexpanded variables** (`$MODEL`, `${MODEL}`, `$(MODEL_ID)`) are never emitted as values.
- **Malformed values are dropped**, not recorded as strings: a typed flag whose value doesn't convert (`--lora_r sixteen`, `--max-model-len abc`), an empty `--model=`, and `nan`/`inf` floats (which would make `spec.data` invalid JSON and unsignable under JCS). `--max-model-len` takes vLLM's human-readable form (`32k` = 32000, `32K` = 32768).
- **Shell comments** (`# ...` to end of line) are dropped after tokenizing. shlex's own `commenters` isn't used because it swallows the newline, merging the lines on either side into one command, and cuts `a/b#c` mid-word. A quoted argument starting with `#` is dropped too. Whole-line comments and heredoc bodies are removed before tokenizing (`_drop_comment_lines_and_heredocs`), since an apostrophe in either (`# axolotl's ...`) left shlex with an unbalanced quote and nothing in the script was detected.

Still not covered: ENTRYPOINT resolution for images other than `vllm-openai`/llm-d and TGI (it would need the Image object), serving flags set only through a config file, and `trl` YAML configs.

trl, Axolotl and LLaMA-Factory are the detected fine-tuning tools. Other serving engines (TensorRT-LLM/Triton) aren't yet supported by any of these layers. TensorRT-LLM in particular has no simple `--model` arg (the model lives in a Triton model repo config), so it needs more than a CLI-name match.

**Quantization from model name**: regex patterns match common quantization markers (`AWQ`, `GPTQ`, `INT4`/`INT8`, `FP4`/`FP8`, `bitsandbytes`/`NF4`, `Marlin`, `GGUF`, `AQLM`, `EXL2`, and others), extracting both method and bit width. Matching is case-insensitive and a marker may be followed by `_` (`fp8_e4m3`). Also covers llama.cpp block types (`Q4_K_M`, `IQ3_XS` -> `gguf`) and llm-compressor names (`w4a16`/`w8a8` -> `compressed-tensors`, bits = weight bits). E.g. `drawais/Granite-3.3-8B-Instruct-AWQ-INT4` detects `awq` at 4 bits.

**Parallelization strategy** (`training.parallelization_strategy`), detected independently of the training tool launched:

- Explicit launcher binary: `accelerate launch --multi_gpu` → `data_parallel`; bare `deepspeed` or `--deepspeed <config>` → `deepspeed`; `torchrun`/`mpirun` → `data_parallel`.
- Bare `--fsdp` flag on the training command itself → `fsdp`.
- Accelerate-launch arguments passed *directly* to a CLI that spawns `accelerate launch` internally (no separate launcher token appears in the command). `trl`'s CLI supports this: `trl sft ... --num_processes 4` → `data_parallel`, and `trl sft ... --accelerate_config <path>` is resolved from the file's actual `distributed_type` (`FSDP` → `fsdp`, `DEEPSPEED` → `deepspeed`, `MULTI_GPU`/`MULTI_CPU` → `data_parallel`) — the harder, easy-to-miss case (see `examples/granite-lora-finetune-multigpu.yaml`).

The `--accelerate_config` file is read from inside the training container itself, by `runtime_detector.py` (the same in-container hook that detects datasets) — `postprocess.py` has no access to the training container's filesystem after the fact. This requires PyYAML in the training image (a hard dependency of `accelerate` itself); if unavailable, or the config's `distributed_type` isn't one of the four listed, detection falls back to guessing from the config filename against known preset names (`fsdp1`/`fsdp2`/`zero1`/`zero2`/`zero3`/`multi_gpu`/`single_gpu`) — a much weaker heuristic that only works if the file is named exactly one of those.

In-script sharding with no command/accelerate-config signal at all — e.g. `device_map="auto"` passed directly to `from_pretrained` in Python, common in raw `transformers.Trainer`/QLoRA scripts with no CLI launcher — is covered by a lowest-priority fallback: the `transformers.PreTrainedModel.from_pretrained` runtime hook (`runtime_detector.py`) captures the `device_map` kwarg and counts the distinct accelerators in the model's resolved `hf_device_map` (`model_device_count`; cpu/disk/meta offload excluded, `cuda`/`cuda:0`/`0` treated as one device), and `postprocess.py` maps a count above 1 to `model_parallel` only if none of the above command/accelerate-config signals produced a strategy first. Counting the resolved map rather than the kwarg is what keeps `{"": 0}`, `cuda:1` and `"auto"` on a 1-GPU pod from reading as `model_parallel` (#109).

## Determinism (#175)

`training.determinism` records the seeds and switches a training run's reproducibility depends on, all from `runtime_detector.py` (`training_determinism` in `postprocess.py` assembles it, `null` when nothing was seen).

- **Seeds.** `random.seed`, `numpy.random.seed` and `torch.manual_seed` (also `torch.random.manual_seed`, the same function) are wrapped, installed through the same post-import finder as the other hooks (`random` and `numpy.random` are triggers of their own; numpy 2 may import `numpy.random` lazily). Each generator's most recent explicit seed is `seeds.<generator>`, since that is the one governing what ran after it, and `seed_history` lists the distinct values in first-seen order (capped at 8) only for a generator seeded with more than one, e.g. a script that seeds 1234 and then lets `Trainer` reseed with 42. `None`, bytes and arrays aren't recorded; strings are truncated to 64 characters and ints past 2^53 become strings, because JCS can't canonicalize them and the compiled AIBOM would silently lose its signature. `training.random_seed` falls back, lowest priority, to the seed every generator agrees on.
- **Whose seeds.** Seeds set inside a `DataLoader` worker are dropped: torch seeds each worker with `base_seed + worker_id` (and NumPy from a derived state) before calling `worker_init_fn`, and transformers' `seed_worker` reseeds again from there. The check walks the stack for `torch.utils.data._utils.worker`, which is on it both for torch's own seeding and for anything `worker_init_fn` or the dataset calls, under fork and spawn. `torch.utils.data.get_worker_info()` would miss the first case, since torch seeds before setting it. Seeds on ranks other than `RANK=0` are dropped too, since accelerate's `set_seed(device_specific=True)` gives each rank `seed + rank`. Verified against torch 2.15 / numpy 2.5 (fork and spawn workers, `torchrun --nproc_per_node=2`).
- **One observation.** A process's seeds live under a single `runtime_info` key, `seeds` (`{"values": {...}, "history": {...}}`), so `_merge_output` and the watcher's first-pod-wins `mergeDatasets` move them as a unit and never pair one process's torch seed with another's Python seed. No Go change was needed for that.
- **Flags.** `cudnn.deterministic`/`.benchmark`, `are_deterministic_algorithms_enabled()` (+ warn-only), `CUBLAS_WORKSPACE_CONFIG`, and `PYTHONHASHSEED` are read at flush time into one `determinism_flags` key, because scripts and `enable_full_determinism` set them by plain assignment or env var. torch is only read from `sys.modules`, never imported. `PYTHONHASHSEED` is read at detector import, since the hash seed is fixed at interpreter start and a later `os.environ` change does nothing. The flags are captured only by a process with training activity (it seeded something, built a `DataLoader` or `TrainingArguments`): `torchrun`'s launcher imports torch and exits after its ranks, and its untouched defaults would otherwise overwrite rank 0's `cudnn_benchmark: true`. A forked child starts with no activity. `TrainingArguments.data_seed` and `full_determinism` come from the existing `__post_init__` hook.
- **Not captured:** local generators (`numpy.random.default_rng`, `RandomState`, `torch.Generator`; `datasets`' `.shuffle(seed=)` uses one, which belongs with #177), `torch.cuda.manual_seed*` on its own, and inference runs (`inference.seed` already covers vLLM's `--seed`; the block only appears for `training`/`sft` intent).

## Experiment Intent Detection

`experiment_intent` (`training`/`sft`/`inference`/`unknown`) gates which top-level sections `compile_aibom` populates at all (`training`, `fine_tuning`, `inference`) — so unlike most other declared/auto-detected fields, getting this wrong doesn't just mislabel one value, it silently drops entire sections. It's filled in from two sources, in order of precedence, mirroring `dataset.declared`/`source_code`'s annotation-first-with-auto-detected-fallback pattern rather than defaulting straight to `"unknown"` whenever nobody set the annotation:

1. **Annotation** — `aibom.io/experiment-intent`, if set.
2. **Inferred from model detection** — `detect_model_from_containers`'s CLI-arg detection (see Model Auto-Detection) already tells us this much for free: any serving invocation (`serving_engine` resolved — vLLM/llm-d, TGI, SGLang, LMDeploy) implies `"inference"`; a trl invocation (`training_framework` resolved) implies `"sft"` if `--use_peft` also resolved an `adaptation_method`, else plain `"training"`.

Whichever source wins is recorded in `experiment_intent_declared_via` (`"annotation"` or `"inferred_from_model_detection"`, `null` if neither resolved anything and it fell through to `"unknown"`), mirroring `dataset.declared.declared_via`.

This only covers the tools `detect_model_from_containers` recognizes (vLLM/llm-d, TGI, SGLang, LMDeploy, trl) — a workload using an undetected tool, or building config directly in Python via `runtime_detector.py`'s runtime hooks with no CLI signal at all, still falls through to `"unknown"` without the annotation. It's also coarser than the annotation: nothing here distinguishes `trl dpo` from `trl sft`, or infers `"unknown"` vs. a genuinely ambiguous mixed workload — it's a best-effort default so common cases (a plain `vllm serve ...` or `trl sft ...` command with no annotation) don't lose their `inference`/`training`/`fine_tuning` sections, not a replacement for setting the annotation explicitly when precision matters.

## Dataset Declaration and Reconciliation

`dataset.declared` is filled in from three sources, in order of precedence:

1. **Annotation** — `aibom.io/dataset-name` (and `dataset-version`/`dataset-source`/`dataset-license`), if set.
2. **CLI arg** — parsed from `--dataset_name`/`--dataset_config_name`/`--dataset_train_split` flags (e.g. `trl sft --dataset_name ...`), if no annotation is set.
3. **Inferred from runtime** — copied from the first `dataset.auto_detected` entry, only if neither of the above produced a name.

Whichever source wins is recorded in `dataset.declared.declared_via` (`"annotation"`, `"cli_arg"`, or `"inferred_from_runtime"`), so it's always possible to tell whether a dataset name reflects something the job author specified or a best-effort guess from runtime observation.

Every entry in `dataset.auto_detected` carries a `matches_declared` boolean, comparing its `dataset_name` against the final `dataset.declared.name` — the actual reconciliation check, flagging when a job declares one dataset but the code loads something different at runtime.

Within `dataset.auto_detected`, `runtime_detector.py` correlates hook detections referring to the same underlying dataset object into a single entry (with a `seen_via` list noting every hook that touched it) rather than recording it twice. The common case: a `datasets.load_dataset(...)` call followed by wrapping the result in a `torch.utils.data.DataLoader(...)`, matched by object identity. Since scripts commonly transform the dataset first (`.map()`/`.filter()`/`.select()`/`.shuffle()`, or re-fetching a split from a `DatasetDict`) before handing it to `DataLoader` — which returns a *new* object each time — correlation falls back to matching on the dataset's stable `(builder_name, config_name, split, cache directory)` identity (the cache directory name hashes the data_files and revision, so two loads of one builder from different files stay apart) when object identity doesn't match, so a transformed dataset still merges into its original entry instead of showing up as a second, generically-named (`"Dataset"`) one. An HF dataset that matches no key at all (saved with `save_to_disk` and reloaded, as axolotl's prepared-dataset cache does, so its cache directory differs) merges into the only `load_dataset` entry when there is exactly one (`_sole_hf_entry`).

Accuracy fixes from #114:

- **Split in the fallback key.** Without it the registry kept whichever load ran last, so a train DataLoader merged into a later `split="test"` entry. A key two loads share (two `json` loads of different files, both split `train`) matches nothing, and the loader gets its own entry. Every split of a returned `DatasetDict` is registered to its entry, and an eval loader on it doesn't replace a train loader's `batch_size`.
- **Dedupe on identity, not name.** `_merge_output` and the watcher's `mergeDatasets` key on name, source, `config_name`, `split`, `revision`, `data_files`, `data_dir`, `root` and `path`, so `load_dataset("json", data_files="train.json")` and `"val.json"`, or MNIST train and test, stay separate. A repeat updates the stored entry, so a `batch_size` added after the first flush isn't lost.
- **File builders are named by their files.** `json`/`csv`/`parquet`/`text`/`imagefolder`/... loads take their name from `data_files` (the one file, the common directory, or the files joined) or `data_dir`, keeping the builder in `builder`.
- **torchvision subclasses.** CIFAR100 inherits CIFAR10's patched `__init__` (EMNIST calls MNIST's), so it recorded both and a CIFAR100 run was declared as CIFAR10. Only the most-derived patched class in the instance's MRO records, so a user subclass still reports its torchvision parent. torchvision instances are also registered for DataLoader correlation.
- **`matches_declared`** ignores case and a leading org or directory (`imdb` ~ `stanfordnlp/imdb`), and is `null` when `declared` was inferred from runtime.
- **CLI config and split.** `--dataset_config_name`/`--dataset_train_split` land in `dataset.declared.config_name`/`split` when the CLI tier wins. A trl `--config` YAML still isn't read, and only the first container with `--dataset_name` is used.

## Git Provenance Detection

`source_code.git_commit`/`git_repository`/`git_branch` covers two distinct scenarios — code baked into the image at build time, and code pulled at runtime by the workload itself (e.g. `sh -c "git clone <url> && python train.py"`) — filled in from five sources, in order of precedence:

1. **Annotation** — `aibom.io/git-repository`/`git-commit`/`git-branch`, if set.
2. **Runtime `.git`-directory read** — `_capture_git_provenance` (`runtime_detector.py`) walks upward (mirroring how `git` itself locates the repo root) from the running script's directory (`__main__.__file__`/`sys.argv[0]`), then from the CWD, looking for `.git`. A `.git` *file* (`gitdir: ...`, a linked worktree or submodule) is followed rather than walked past, which used to report the superproject; a worktree's refs and config are read from its `commondir`. It resolves `HEAD` to a commit (following a loose ref file, itself possibly a symref, or falling back to `packed-refs`; anything that doesn't end in a full SHA is dropped), records the branch as everything after `refs/heads/` (`feature/foo`), reads the `origin` remote URL (else the first remote, e.g. after `clone --origin upstream`) straight out of `.git/config` (no dependency on the `git` binary being installed), and best-effort shells out to `git status --porcelain -uno` (untracked files such as checkpoints written into the repo don't count) for a dirty-tree check if `git` happens to be available (recorded as `source_code.dirty`; omitted entirely, not reported as clean, if it can't be determined). Ranked highest among auto-detected sources because it reflects the actual final checked-out state — after any `git checkout`/`git pull` beyond the initial clone — not just intent.
3. **CLI-parsed `git clone`/`checkout`** — `detect_git_clone_from_containers` (`postprocess.py`) reads the container's own command/args (the same tokens the vLLM/trl CLI detectors already see, including through the `sh -c`/`bash -c` wrapper-script flattening), one command at a time: `git clone` (skipping option values like `--reference <path>`, so they aren't taken as the repo), and later `git checkout`/`git switch` (`-b <new> [<start>]`, `--detach`, `git -C <dir>`). Each checkout is applied to the clone it runs in by following `cd` and `-C` (matched by directory basename); with one clone, a checkout whose location can't be told applies to it. With several clones (code plus an HF dataset repo, say), the one the script last `cd`s into is reported, else the first, so repo and commit always come from the same clone. A hex ref of SHA length (7-40, or 64 for SHA-256) that isn't all digits is a commit; anything else a branch/tag (so `20240101` is a tag, but a branch named `cafe123` still reads as a commit). `FETCH_HEAD`/`HEAD`/unexpanded `$VARS` say nothing, and clear any earlier ref for that clone. Falls back below the `.git`-directory read (which reflects a script's actual outcome, not just its stated command) but ranks above the image-label tiers below, since it's still specific to *this run's* command rather than a label baked onto the image at build time.
4. **OpenShift BuildConfig commit labels** — if none of the above resolves anything, `detect_git_provenance_from_containers` (`postprocess.py`) looks up the container's image by digest (`containers.json`'s `image_id`, populated in the watcher from `ContainerStatuses[].ImageID` — the resolved digest, not the mutable tag a re-push could spoof) against the cluster-scoped `image.openshift.io` `Image` object, and reads whatever `io.openshift.build.commit.id`/`.ref`/`.source-location` labels OpenShift's build controller baked onto it. A bare `sha256:` `image_id` (the config digest, which some runtimes report) falls back to a digest-pinned spec `image`; a manifest list's `Image` has no labels of its own, so its per-platform images are tried. Sidecar containers (`istio-proxy`, `queue-proxy`, ours, ...) are skipped. Labels inherit through `FROM`, so if this tier's commit and the OCI revision label below disagree, one of them belongs to a base image and both are ignored; an image with no labels of its own still reports whatever its base carried, which labels alone can't detect.
5. **OCI-standard image labels** — if no OpenShift-specific labels are present either, falls back to the vendor-neutral `org.opencontainers.image.revision`/`.source` labels on the same `Image` object's config. These are set by tooling other than an OpenShift `BuildConfig` (GitHub Actions' `docker/metadata-action`, `docker buildx build --label`, Cloud Native Buildpacks, `ko`, Jib, ...), so this extends detection to images built by any CI system that follows the OCI convention — not just in-cluster builds. There's no standard OCI label for the branch, so this tier only ever yields commit + repository, never `git_branch`.

**Labels from the registry.** An `Image` object exists only on OpenShift, and only for images OpenShift imported (its internal registry, ImageStreams), so a quay.io/ghcr.io image has none even there. When the lookup returns no labels, `_registry_image_labels` reads the image config from the registry itself: the manifest by the container's digest, an index's first non-attestation child (an index's platforms come from one build, so their labels match), then the config blob, and both tiers above apply to its labels unchanged. Auth is the Docker v2 anonymous bearer-token flow only, since postprocess has no pull secrets (giving it any would mean Secret read access in every workload namespace), so private images are skipped with a warning. Every response is hashed and must match the digest it was fetched by, which keeps the tiers' digest-keyed property: the labels are those of the exact image that ran. Requests are https only, capped at 4 MiB and 10 s, and redirects (Docker Hub serves blobs from a CDN) are followed by hand so the token isn't sent to another host. The registry host comes from the kubelet-reported `imageID` or a digest-pinned spec image, i.e. somewhere the node actually pulled from, but the token `realm` is whatever that registry says, so a hostile registry can make postprocess issue GETs to a URL of its choosing (no credentials attached). `--registry-label-lookup`/`gitProvenance.registryLookup` (default on, `AIBOM_REGISTRY_LABEL_LOOKUP` on the Job) turns it off for clusters without egress, where each attempt would otherwise wait out its timeout, or to stop the outbound requests.

If none of the above resolves anything (a prebuilt image with no CI-stamped provenance, no `.git` directory present, running a command with no visible `git clone`), this falls through to nothing. RBAC for the `Image` lookup (`aibom-postprocess-images` ClusterRole, bound once to the webhook namespace's `aibom-postprocess` ServiceAccount, both rendered only on OpenShift) is intentionally narrow — `get` on `images` only, nothing else in `image.openshift.io`.

Whichever source wins is recorded in `source_code.declared_via` (`"annotation"`, `"git_directory"`, `"cli_arg"`, `"openshift_build_label"`, or `"oci_image_label"`), mirroring `dataset.declared.declared_via`. Sources aren't all-or-nothing (#113): `merge_provenance` fills the fields a higher tier lacks (a `.git` with no remote) from the next one, and the annotations' missing fields from detection, but only when the two don't name a different commit (an abbreviated SHA matches its full form) or repository (compared without scheme, credentials, `.git` or case) — otherwise they describe different checkouts and nothing is mixed in. The image lookup only runs while commit or repository is still unknown. Any `aibom.io/git-*` annotation makes `declared_via` `"annotation"`. `source_code.dirty`, only ever known from the `.git`-directory tier, is kept as long as that tier's checkout is the one reported.

**Credential redaction (#102).** A clone URL can embed a token (`https://user:ghp_...@host/repo`, which `git clone` stores verbatim in `.git/config`), and `source_code.git_repository` ends up in the signed, immutable `spec.data` and in any archived copy. `redact_git_url` (`postprocess.py`; `_redact_git_url` in `runtime_detector.py`, duplicated because the detector is mounted alone and stays stdlib-only) strips it: for http(s)/ftp the whole userinfo (a bare username is often the token), for other schemes only a password (`ssh://git@host` keeps `git`), and the query string and fragment always (`?token=`, `?private_token=`). scp-style `git@host:org/repo` has no scheme and is left alone. It runs where each tier reads a URL (`.git/config`, the CLI parse, the runtime-info tier, both image-label tiers), when `dataset.json`'s `runtime_info` is loaded (older pods may have written an unredacted URL, and `compile_aibom` logs it), and finally on the winning value in `compile_aibom`, which also covers the free-text `aibom.io/git-repository` annotation. Redaction is not retroactive: AIBOMs already created, and their data ConfigMaps, keep whatever was recorded. Other fields aren't scanned: a credential in a container's command or args elsewhere isn't recorded in the AIBOM, but that is by absence rather than a filter.

**This is identification, not verification, and it isn't a security/compliance artifact.** The image-label tiers record what the build controller believes it cloned — not that nothing was injected into the image afterward (e.g. an extra `RUN` step after the `git clone`), and not that the source was vetted. Digest-keying only protects against a re-tagged image claiming someone else's labels; it does nothing about a workload that simply never went through a labeled build in the first place. The CLI-parsed tier is weaker still — it reports what the command *says* it will clone, not what actually landed on disk. Even the `.git`-directory tier, the strongest of the auto-detected sources, only reflects what's on disk at the moment `runtime_detector.py`'s `atexit` hook fires — a script could still delete or rewrite `.git` afterward, or never trigger the hook at all (a non-Python container, or an interpreter started with `-I`, `-E` or `-S`, which ignore `PYTHONPATH` or skip `sitecustomize` entirely). Detections are now also flushed shortly after they happen (see Runtime Detection Output Durability above), so an `atexit` that never runs (SIGKILL/OOM, SIGTERM under Python's default handler) no longer loses everything — but git provenance is still best-effort: it's captured at the first flush and re-captured at exit, so a kill before the exit-time re-capture leaves the first observation, and the dirty flag in particular reflects the tree at that earlier moment (#107). Reaching genuine tamper-evident provenance would require a signed attestation (e.g. Tekton Chains/SLSA, verifiable independent of trusting the live cluster) plus admission-time enforcement rejecting unsigned images — both out of scope here; this only records what's cheaply available and labels its source honestly.

`pip install git+...`'s PEP 610 `direct_url.json` isn't implemented.

## Prometheus Telemetry

`postprocess.py` queries Prometheus/Thanos Querier directly (`PROMETHEUS_URL`, defaulting on OpenShift to `https://thanos-querier.openshift-monitoring.svc:9091` and to empty, i.e. telemetry off, elsewhere — see `charts/aibom-webhook/values.yaml`'s `prometheus.url`). There's no separate credential to provision: auth and TLS trust are both automatic, mirroring gpu-quota-operator's `metrics.Client` (`metrics/prometheus.go`) exactly —

- **Auth**: the postprocess Job's own ServiceAccount token (`/var/run/secrets/kubernetes.io/serviceaccount/token`, auto-mounted and rotated in place by Kubernetes) is read fresh on every request and sent as a Bearer token. Authorization on the Thanos Querier side comes from a `cluster-monitoring-view` ClusterRoleBinding that `charts/aibom-webhook/templates/postprocess.yaml` creates once for the webhook namespace's `aibom-postprocess` ServiceAccount (`monitoringAccess.enabled`, default `true`, on the webhook chart; set it false for accounts without cluster-scoped RBAC permission).
- **TLS**: the cluster's service-serving CA bundle is injected into the `aibom-service-ca` ConfigMap (`service.beta.openshift.io/inject-cabundle` annotation, in the webhook chart) and mounted into the postprocess Job as *optional* — on a cluster with no service-ca operator, or a plain-HTTP dev Prometheus that doesn't need TLS at all (e.g. `mock-openshift-cluster`'s), the mount resolves to an empty directory and the client falls back to the system trust store rather than erroring.

Neither file being present is a hard requirement in either direction — a missing token means requests just go out unauthenticated, and a missing CA bundle means the system trust store is used instead. Both fall back gracefully rather than failing the Job.

## Telemetry Retries

`postprocess.py` queries Prometheus immediately after the workload's pod completes. On some observability backends (e.g. a federated/multi-tenant Prometheus setup) there's a delay between a metric being scraped and it becoming queryable, so a query fired this soon can race that delay and come back empty even though the identical query succeeds moments later — this shows up as `resource_utilization` metrics being present on some AIBOMs and missing on others for no apparent reason, even though the same query run moments later returns the data.

To absorb this, metrics with no data points are retried with a delay (`AIBOM_TELEMETRY_RETRY_ATTEMPTS`, default `3`; `AIBOM_TELEMETRY_RETRY_DELAY_S`, default `45` seconds between attempts) before being recorded as unavailable — only the metrics still missing on a given attempt are re-queried, not the whole batch.

### Segmented Performance Stats

Each telemetry metric (`gpu_utilization`, `gpu_memory_used`, `gpu_power`, `cpu_usage`, `memory_usage`, `network_receive`, `network_transmit`, `storage_read_throughput`, `storage_write_throughput`) is queried once as a Prometheus **range** query, over the same cold-start-excluded window an averaged summary query would have used — there's no separate instant `avg_over_time` query per metric. Each query aggregates in PromQL to exactly one series per pod — `sum` across containers/GPUs/interfaces, `avg` for GPU utilization — matching the time series' per-run `aggregate` lines; `parse_range_response` pools every series it gets back, so an unaggregated query would average a pod's 8 GiB app container with its 50 MiB sidecar and report ~4 GiB. Queries are scoped to the workload's namespace (`exported_namespace` for DCGM), and CPU/memory/storage exclude `aibom-dataset-sidecar`, the same `_WORKLOAD_CONTAINERS` filter the series use.

**Window.** `_pod_stats_window` runs from the pod's `start_time` (parsed as UTC, like the series path) to the latest `finished_at` of its containers — captured by the watcher from `ContainerStatuses[].State.Terminated.FinishedAt` into `containers.json` — or to now if any container hasn't finished (e.g. the bare-pod finalizer path). It doesn't end at collection time because every query's `[5m]` window keeps returning a stopped pod's last samples for up to five minutes afterwards, which skewed the last third of short runs. The first scrape interval (`SCRAPE_INTERVAL_S`, 30 s, the same `AIBOM_SERIES_SCRAPE_INTERVAL_S` the series use) is excluded as cold start, capped at half the run; a run too short for that is flagged via `summary_includes_cold_start`. `execution_metadata.duration_seconds` uses the same end point (the last pod's finish).

**Rounding and units.** `compute_metric_stats` keeps full precision; `aggregate_pod_metrics` rounds once, after scaling to the display unit, to 2 decimals at magnitude ≥ 1 and 3 significant figures below that (`_round_stat`), so small values like a 14 ms inter-token latency or 0.0006 cores aren't rounded to zero. Memory is reported in GiB (binary, like a Kubernetes `8Gi` limit); network (`Mbps`) and storage (`MBps`) rates are decimal. `compute_metric_stats` (`postprocess.py`) then reduces that one range response to `min`/`max`/`avg`/`p95`, plus an `avg` over each of the run's first/middle/last thirds (`segments`), instead of collapsing straight to a single average. A flat average can't tell a run that held steady apart from one that started hot and throttled down, or one with a mid-run stall (a checkpoint pause, a data-loader stutter) — the three segments make that shape visible without storing the full series (which would make `resource_utilization`'s size scale with run duration, a bad fit given `spec` is immutable once the AIBOM CR is created).

This lands in `resource_utilization` as a single `resource_utilization.metrics.<name>` object per metric, carrying the full `min`/`max`/`avg`/`p95`/`segments` breakdown. The earlier pre-segmentation flat fields (`avg_gpu_utilization_pct`, `avg_cpu_usage_cores`, etc.) have been removed from the AIBOM; `oc-aibom`'s sort/filter/diff logic reads `metrics.<name>.avg` instead (see `ResourceUtilization.MetricAvg` in `oc-aibom`). For a JobSet's sibling pods, `min`/`max` take the true extreme across all pods (a single pod's outlier is still real), while `avg`/`p95`/`segments` are averaged across pods — an approximation, since a true cross-pod percentile would need every pod's raw series merged first, which isn't worth the added complexity here.

`memory_usage`/`cpu_usage` additionally carry a `limit` field (`compute_metric_limit` in `postprocess.py`) — the configured Kubernetes resource limit usage was measured against, scaled the same way `min`/`max`/`avg` already are so the two read as directly comparable (e.g. "used 7.8 of an 8.0 GiB limit"). The limit itself comes from `Spec.Containers[].Resources.Limits`, captured in `containers.json` by the watcher's `buildPostprocessInputs` (`memory_limit_bytes`/`cpu_limit_millis`) — known at pod-creation time, unlike [Pod Termination Status](#pod-termination-status)'s fields, which only exist after the pod has actually finished. A pod's own multi-container limit sums across its containers (`pod_resource_limit`), the same cgroup-level rollup the kubelet enforces; across a JobSet's sibling pods, the *tightest* limit wins, not an average or the true max/min the other stats use — the ceiling closest to actually constraining usage is the useful one to surface, even if a looser-limited sibling used more memory in absolute terms. Omitted entirely (no `limit` key, not `null`) when no container in the workload set a limit for that resource, or for any other metric (`gpu_utilization`, `network_receive`, etc.) that has no Kubernetes resource-limit concept to report.

This is deliberately paired with [Pod Termination Status](#pod-termination-status) rather than replacing it: `status: "OOMKilled"` tells you a container was killed; `metrics.memory_usage.limit` tells you what it was killed *against*. Neither alone answers "how close did this get" as well as both together — a `memory_usage.max` sitting near (or exactly at) `.limit` on a `Completed` pod is itself a useful near-miss signal that no explicit status field would ever surface.

Full-resolution time-series data is deliberately not stored anywhere in the AIBOM; the downsampled `AIBOMTelemetry` series (see Telemetry Time Series) is the closest thing, and live Prometheus has the rest while it's retained.

A pod with no detected GPU (`gpu_count` 0 or missing in its discovery data, e.g. `nvidia-smi` found no hardware) is skipped for telemetry entirely — there's no GPU utilization to query, so it's omitted rather than querying anyway. On a mock cluster (e.g. kind) with no real GPU hardware, `nvidia-smi` always reports zero GPUs, so every pod gets skipped and telemetry collection never runs at all. `--debug-telemetry-all-pods` (`debug.telemetryAllPods` chart value, plumbed to the postprocess Job as `AIBOM_DEBUG_TELEMETRY_ALL_PODS`) bypasses this check so telemetry is queried for every pod regardless of detected GPU count — for local testing only, not routine production use.

## Telemetry Time Series

The summary stats above deliberately keep no series (`spec` is immutable and sized for a small object), and cluster Prometheus retention (~15 days) means a UI that charts live from Prometheus (the `aibom-console-plugin`) shows nothing for older AIBOMs. So `postprocess.py` also persists a **downsampled** copy of each metric's series at collection time, while Prometheus still has it. It is entirely additive: no summary-stat field or behavior changed, and an AIBOM without it is fully valid (readers fall back to live Prometheus).

**Storage: a dedicated `AIBOMTelemetry` custom resource, referenced from the signed AIBOM.** Inline in `spec.data` would make every AIBOM list/watch carry ~100 KB+ per row (the console plugin's list page watches every AIBOM but never uses the series), and per-pod/per-GPU detail can approach the ~1.5 MB etcd object cap. A ConfigMap avoids that but clutters the namespace's ConfigMap list, and is writable by every workload ServiceAccount through `aibom-workload-data`'s broad Role (see `ValidateSigningPublicKeyConfigMap`'s doc comment for the same problem) — it would have needed its own admission guard. `aibomtelemetries.aibom.io` (kind `AIBOMTelemetry`, `v1alpha1`, namespaced, short name `aibomtel`, category `aibom`; defined next to the AIBOM CRD in `charts/aibom-webhook/crds/aibom-crd.yaml`, so the existing `oc apply -f` steps cover both) has neither problem: it stays out of the ConfigMap list, the AIBOM watch never sees it, and only `aibom-postprocess` is granted the kind at all, so no workload pod can forge or overwrite one. Its `spec` is CEL-immutable like the AIBOM's, and it has no `status`.

`publish_series_object` creates one per AIBOM, named `<job-name>-telemetry-<random>` (the AIBOM itself uses `generateName`, so its name isn't known up front; readers must use the name in the reference, never a naming convention), in the AIBOM's namespace, labeled `aibom.io/job-name`. Spec fields: `seriesJson` (string), `schemaVersion`, `sizeBytes`, `window{start,end,stepSeconds}` — the last three only for `kubectl` readability (`oc get aibomtel` shows owning AIBOM, size, window end).

- **`seriesJson` is a string, not structured YAML**, so a reader can hash precisely what was stored and compare it to the signed digest. Re-serialized structured JSON can't be hashed reliably without an RFC 8785 canonicalizer, which the console plugin doesn't have. Capped by the CRD at `maxLength: 900000`.
- **Order matters.** The reference must be inside the *signed* `spec.data` (spec is CEL-immutable, so it can't be added later), and the digest has to exist before that. So the `AIBOMTelemetry` is created first, then the AIBOM (signed over `data` including the reference), then the `AIBOMTelemetry` is PATCHed with an `ownerReference` (`blockOwnerDeletion: true`) to the AIBOM. Garbage collection then deletes it with the AIBOM.
- **Integrity.** The object's content isn't itself signed; `spec.data.telemetry_series_ref.sha256` (hash of the exact `spec.seriesJson` string, UTF-8) is, so a verifier checks the object against the signed digest. `oc-aibom` does this (`aibom.VerifySeries`, the `Telemetry Series:` line of `oc aibom describe`): it hashes `spec.seriesJson` and compares it and `size_bytes` to the reference read from the same generic `spec.data` tree the AIBOM signature covers. A matching series is reported as fully Verified only if the AIBOM's own signature is Valid — the digest lives inside `spec.data`, so without a trustworthy signature over it, whoever could forge the series could forge the digest too — and as digest-only otherwise. The console plugin is expected to do the same check in the browser; nothing else in the pipeline verifies it, so the only other protection is that only `aibom-postprocess` can write the kind.
- **Failure modes.** Prometheus down/empty, size cap exceeded, or the object create denied (e.g. an old namespace without the new CRD/Role, or a `count/aibomtelemetries.aibom.io` ResourceQuota) → the AIBOM is created without `telemetry_series_ref` (a warning is logged; the Job doesn't fail). If AIBOM creation fails after the object exists, the object is **orphaned, not deleted**: `aibom-postprocess` deliberately has no `delete` on `aibomtelemetries` (see RBAC below), so the Job logs a warning with the `oc delete aibomtel <name> -n <ns>` command and exits non-zero, and its retry stores a fresh object. If the owner PATCH fails, the object is likewise orphaned (still labeled `aibom.io/job-name`) — logged. A Job attempt that dies between the object create and the AIBOM create leaves an orphan too; the random name means a retry never collides with it. Orphans only accumulate for failing runs; find them with `oc get aibomtel -A` (an empty AIBOM column, since it's derived from `ownerReferences`) or by `aibom.io/job-name`.
- **RBAC.**
  - `aibom-postprocess` Role (`charts/aibom-workload-namespace/templates/rbac.yaml`): `aibomtelemetries` create/patch, plus `aiboms/finalizers` update — OpenShift's owner-reference permission enforcement requires it to set `blockOwnerDeletion: true` on an owner (`AIBOM` has no real `finalizers` subresource, so this is very likely only a permission-check placeholder, but that hasn't been tested on a live cluster). Names are random per run, so this can't be `resourceNames`-scoped — which is why **`delete` is withheld**: it would let a compromised postprocess erase every other run's series in its namespace, a wider blast radius than its `aiboms` grant (create/get only). `spec` is CEL-immutable, so `patch` can only touch metadata (the ownerReference). No ConfigMap grant was added for this.
  - Viewers: the `aibom-view` ClusterRole (`charts/aibom-webhook/templates/aibom-view-clusterrole.yaml`, aggregated into `view`/`edit`/`admin`) now lists `aibomtelemetries` next to `aiboms` (get/list/watch). The standard `view` role doesn't cover custom kinds, so this is what lets a viewer's own token read them; nothing cluster-wide beyond that.
- **Upgrading existing namespaces.** They need the new CRD (`just deploy` re-applies `aibom-crd.yaml` every run, or `oc apply -f` it after `--skip-crds`), the webhook chart upgrade for the `aibom-view` change, and an `aibom-workload-namespace` chart upgrade for the postprocess Role. Until all are in place, runs still produce AIBOMs, just without series.

**Reference, at `spec.data.telemetry_series_ref`:**

```json
{"schema_version": 1, "kind": "AIBOMTelemetry", "name": "<object name>",
 "sha256": "<hex of spec.seriesJson>", "size_bytes": 12345,
 "window": {"start": 1767225600, "end": 1767229200, "step_seconds": 30}}
```

(The first version of this feature stored the series in a ConfigMap instead, with `configmap` and `key` in place of `kind` and `name`; those AIBOMs aren't migrated, and readers should accept both shapes.)

**Document, at `AIBOMTelemetry.spec.seriesJson`** (compact JSON string, `sort_keys`):

```json
{"schema_version": 1,
 "window": {"start": <unix s>, "end": <unix s>, "step_seconds": <int>},
 "pods": ["..."],
 "metrics": {
   "<metric key>": {
     "unit": "cores", "aggregation": "sum|avg",
     "aggregate": [[<unix s>, <value>], ...],
     "aggregate_max": [[<unix s>, <value>], ...],
     "series": [{"labels": {"pod": "...", "container": "...", "interface": "...", "gpu": "..."},
                 "points": [[<unix s>, <value>], ...]}],
     "series_omitted": true
   }}}
```

- **Timestamps are integer unix seconds (UTC)** — no timezone suffix to misread, unlike the pod `start_time` strings.
- **Metric keys** are the same as `resource_utilization.metrics` (`gpu_utilization`, `gpu_memory_used`, `gpu_power`, `cpu_usage`, `memory_usage`, `network_receive`, `network_transmit`, `storage_read_throughput`, `storage_write_throughput`) and `inference.performance.metrics` (`time_to_first_token_seconds`, `inter_token_latency_seconds`, `num_requests_running`, `num_requests_waiting`, `kv_cache_usage`, `prompt_throughput`, `generation_throughput`; vLLM pods only). Only metrics that returned data are present.
- **Units are raw base units** (`bytes`, `bytes_per_sec`, `cores`, `MiB`, `watts`, `percent`, `seconds`, `requests`, `tokens_per_sec`), *not* the display-scaled units (GiB/Mbps/MBps) `resource_utilization` reports — the reader scales.
- **`aggregate` is the per-run line** (the default chart): `sum` across all series for memory/CPU/network/storage/GPU memory/GPU power/queue depth/throughput, `avg` for utilization, KV-cache and latency (an unweighted mean across pods — not request-weighted). `aggregate_max` exists only for gauge metrics and is the per-bucket peak (max across series for `avg` metrics; sum of each series' own bucket peak for `sum` metrics, a slight upper bound) so a spike shorter than the step survives downsampling.
- **`series` is the optional per-pod expansion**: labels are `pod` (+ `container` for CPU/memory, `interface` for network, `gpu` for GPU metrics; GPU series carry the workload's `exported_pod`, normalized to `pod`). It's dropped (`series_omitted: true`) for a metric with more than 64 series (`AIBOM_SERIES_MAX_SERIES_PER_METRIC`) regardless of size. `aggregate` is never dropped.
- **Size cap, and what gives first.** The whole document is capped at 900 000 bytes (`AIBOM_SERIES_MAX_BYTES`, matching the CRD's `seriesJson` `maxLength` and well under etcd's ~1.5 MB object limit). The number of points isn't capped directly: the step is `ceil(run length / 200)` (`AIBOM_SERIES_TARGET_POINTS`), floored at the Prometheus scrape interval (`AIBOM_SERIES_SCRAPE_INTERVAL_S`, default 30 s, OpenShift's default) — a gauge bucket (and its `_over_time` window, which equals the step) narrower than the scrape interval can hold no sample and come back empty — so a line never has more than ~201 points, and runs under ~100 minutes have fewer (a 20-minute run gets 40 points at 30 s). If the document is still over the byte cap, `_fit_series_doc` shrinks it in this order: **(1) reduce resolution** — re-bucket everything 2×, 3×, … coarser (always from the original, so factors don't compound) for as long as every line keeps at least 100 points (`AIBOM_SERIES_MIN_POINTS`); **(2) only then drop per-pod/per-GPU `series`**, largest metric first. Resolution goes first because per-GPU history is the one thing only this feature can show. Re-bucketing averages `aggregate` and `series` per bucket and takes the *max* for `aggregate_max` (already a per-bucket peak), so a spike survives as its merged bucket's peak; `window.step_seconds` is updated to the coarser step, and bucket timestamps stay on the original grid. In practice only one halving is possible (200 → 100 points). Typical sizes: ~40 KB (1 pod, 1 GPU, 20 min), ~190 KB (1 pod, 8 GPUs, 12 h), ~575 KB (4 pods × 8 GPUs, 12 h), ~555 KB at 100 points (8 pods × 8 GPUs, 24 h, which would otherwise have lost detail). A run with more than 64 series per metric (e.g. 16 pods × 8 GPUs) still loses that detail, since that rule doesn't depend on size. These limits are module constants read from environment variables that the watcher/chart don't set, so the defaults are what runs.

**Collection.** `collect_telemetry_series` runs after the stats collection and its retries (no retries of its own). Unlike the stats path it uses one range query per metric for *all* pods (`pod=~"a|b|c"`, filtered by `namespace`), over the **full window** (earliest pod start → the last pod's finish time, or collection time if a pod hasn't finished; no cold-start trim), with the step chosen to land near 200 points (`AIBOM_SERIES_TARGET_POINTS`, floored at the scrape interval, see Size cap). Gauges use `avg_over_time`/`max_over_time` over the step so buckets tile rather than sampling single instants. Per-container CPU/memory/storage queries exclude the `aibom-dataset-sidecar` container (`container!="aibom-dataset-sidecar"`), the same as the stats queries.

**GPU series.** The postprocess ServiceAccount already reads cluster-wide metrics via `cluster-monitoring-view`, and the DCGM series are filtered on `exported_namespace`/`exported_pod` (the workload's identity — DCGM's own `namespace` label is `nvidia-gpu-operator`), so per-GPU (`gpu` label) series are recorded. This is the only place per-GPU history is kept, since a viewer without cluster-wide metrics access can't query DCGM live. It needs dcgm-exporter's pod mapping enabled (otherwise `exported_pod` doesn't exist and the metric is simply absent).

**Window start time.** `_parse_start_utc` treats a suffix-less `start_time` as UTC, in both the stats and series paths. The discovery init container writes `datetime.now().isoformat()` (its local time, no suffix), so this is only correct if the discovery image runs in UTC (the default for container images); the postprocess container's own time zone no longer matters.

## Inference Performance Telemetry

`resource_utilization` (above) is a hardware-level view — was the GPU/CPU/network busy — which is what a training run's operator cares about, but it's the only telemetry an inference AIBOM got before this section existed. The serving engines [Model Auto-Detection](#model-auto-detection) recognizes (vLLM/llm-d, TGI, SGLang, LMDeploy) each expose their own native `/metrics` endpoint with the actual serving-level SLOs: TTFT/ITL latency, queue depth, KV-cache utilization, and token throughput. These land in a separate top-level `inference.performance` section, not folded into `resource_utilization`, since they describe the *application's* behavior ("were requests queueing, was the KV cache thrashing"), not the hardware underneath it.

**All four engines expose the same metric *shapes*** — TTFT/ITL histograms, running/waiting gauges, a KV-cache gauge, prompt/generation token counters — differing only in metric names. So rather than hand-writing four copies of the query dict, a per-engine name table (`SERVING_ENGINE_METRICS`) is fed to `_build_serving_queries`, which generates both the per-pod stats queries (`SERVING_TELEMETRY_QUERIES[engine]`) and the by-pod time-series queries (`SERVING_SERIES_QUERIES[engine]`). The generator reproduces the hand-verified vLLM queries byte-for-byte (`test_build_serving_queries_reproduces_vllm`), which is what lets every other engine inherit their confirmed correctness. `VLLM_TELEMETRY_QUERIES`/`VLLM_SERIES_QUERIES` remain as aliases for `["vllm"]`.

**Metric names confirmed against each engine's own docs** (not guessed from memory, per the caution that also applies to #84's Pure Storage findings):
- **vLLM** (live 0.17 server): `vllm:time_to_first_token_seconds`/`vllm:inter_token_latency_seconds` (histograms), `vllm:num_requests_running`/`vllm:num_requests_waiting` (gauges), `vllm:kv_cache_usage_perc` (0–1 gauge, ×100 to match `percent`), `vllm:prompt_tokens_total`/`vllm:generation_tokens_total` (counters). Older releases used `vllm:time_per_output_token_seconds` (ITL) and `vllm:gpu_cache_usage_perc` (KV-cache); both queries fall back to the old name with PromQL `or`, aggregated to one series so a server exporting both reports only the new one.
- **LMDeploy** (its `metrics/loggers.py`): mirrors vLLM's names under the `lmdeploy:` prefix (`lmdeploy:time_to_first_token_seconds`, `lmdeploy:time_per_output_token_seconds`, `lmdeploy:num_requests_running`/`_waiting`, `lmdeploy:gpu_cache_usage_perc`, `lmdeploy:prompt_tokens_total`/`generation_tokens_total`).
- **SGLang** (production_metrics docs): `sglang:time_to_first_token_seconds`, `sglang:request_time_per_output_token_seconds`, `sglang:num_running_reqs`/`sglang:num_queue_reqs`, `sglang:token_usage` (0–1 KV-cache fraction, ×100), `sglang:prompt_tokens_total`/`generation_tokens_total`.
- **TGI** (HF metrics reference): different shape — no colon prefix, and **no TTFT or KV-cache metric at all**, so it reports only a subset (`tgi_request_mean_time_per_token_duration` → ITL, `tgi_batch_current_size` → running, `tgi_queue_size` → waiting, `tgi_request_input_length_sum` rate → prompt throughput, `tgi_request_generated_tokens_sum` rate → generation throughput; the token counts are per-request histograms, whose `_sum` is the cumulative token count vLLM's `_total` counters are). TGI times queueing (`tgi_request_queue_duration`, per request) and prefill (`tgi_batch_forward_duration{method="prefill"}`, per batch) separately, but adding a per-request and a per-batch average isn't a per-request TTFT, so none is synthesized; `tgi_batch_current_max_tokens` is the batch's token budget, not KV-cache occupancy. Checked against a live TGI 3.0.1 `/metrics`. Since the `inference.performance` unit map is the same canonical set for every engine, a metric an engine doesn't export is simply absent from the pod telemetry and skipped.

Collected by `collect_vllm_telemetry` (`postprocess.py`), which takes an `engine` arg selecting the query set — a separate pass from `collect_telemetry`'s `TELEMETRY_QUERIES`, same per-pod retry/cold-start machinery, only ever invoked from `main()` when `detected_model.serving_engine` is one of the engines in `SERVING_TELEMETRY_QUERIES`.

**The engines' own metrics carry no pod/namespace label** (vLLM emits just `engine`/`model_name`). Every query here filters on `namespace`/`pod` labels the engine never emits; they only exist because the `aibom-vllm-metrics` `PodMonitor` (`charts/aibom-workload-namespace/templates/monitoring.yaml`, gated behind `vllmMetrics.enabled`, default `false`) causes Prometheus's target-discovery relabeling to attach them — the same mechanism the cAdvisor `container_*` queries rely on. A `PodMonitor`, not a `ServiceMonitor`: KServe's predictor `Service` only exposes port 80, never the engine container's own serving port, so a `ServiceMonitor` scraping through the `Service` wouldn't reach it.

The `PodMonitor`'s selector is `aibom.io/instrumented: "true"` (the same label the webhook already stamps on every qualifying pod), with one endpoint per engine's own upstream default port (vLLM 8000, TGI 80, SGLang 30000, LMDeploy 23333), plus 8080 for TGI: OpenShift's restricted SCC runs pods as a random non-root UID without `NET_BIND_SERVICE`, so TGI can't bind 80 there and runs on 8080 instead, as KServe's TGI runtime does. vLLM also gets 8200 (#166): an llm-d decode pod puts its routing sidecar on 8000 and moves vLLM to 8200 (llm-d-modelservice's `routing.proxy.targetPort` default). The sidecar reverse-proxies every path it doesn't handle itself, `/metrics` included, to vLLM, so scraping both ports would record each vLLM series twice and double the summed counters and gauges. Every endpoint therefore drops targets with `__meta_kubernetes_pod_container_init=true`: the sidecar is a native sidecar (an init container with `restartPolicy: Always`), and no serving engine runs as one. A `targetPort` only matches a port the container declares, so vLLM on 8200 has to declare it (llm-d's recipes do; the modelservice chart leaves it commented out). This is a deliberate simplicity tradeoff: teaching the Go mutator which engine (if any) a pod runs at admission time — to stamp an engine-specific label and scope a single scrape target — would mean duplicating `postprocess.py`'s CLI-detection logic in Go. A pod that isn't a given engine just doesn't listen on that port (the scrape fails, harmless), and the prefixed metric names (`vllm:`/`sglang:`/`lmdeploy:`/`tgi_`) never match anything unrelated. A workload that overrides a port isn't scraped — an accepted, documented gap (#86), not solved by a per-workload override yet. SGLang additionally needs `--enable-metrics` for anything to be on `/metrics`, as did LMDeploy before 0.18; TGI and LMDeploy 0.18+ expose metrics by default (0.18 replaced the flag with an opt-out `--disable-metrics` and rejects `--enable-metrics`).

TTFT/ITL are histograms, not gauges — `time_to_first_token_seconds_sum{...}` rate divided by `time_to_first_token_seconds_count{...}` rate gives the average latency per time window, which `compute_metric_stats` then reduces the same way as every gauge metric (`min`/`max`/`avg`/`p95`/`segments`, see Segmented Performance Stats above) for consistency with the rest of the telemetry pipeline. That "p95" is honestly a p95 of the *windowed average* latency, not a true per-request percentile (which would need `histogram_quantile()` over the raw bucket series) — a known simplification, not a second differently-shaped stats structure for just these two metrics. A window with zero completed requests divides 0/0 into `NaN`; `parse_range_response` drops `NaN` samples rather than letting them silently corrupt `min()`/`max()`/`sum()` reductions.

## Non-OpenShift Clusters

Both charts have a `platform` value (`auto`/`openshift`/`kubernetes`); `auto` checks `.Capabilities.APIVersions.Has "image.openshift.io/v1"` (`aibom-webhook.openshift` / `aibom-workload-namespace.openshift` helpers). Like the signing keys' `lookup`, this sees nothing under an offline `helm template` (Argo CD's default), which renders the non-OpenShift branch, so offline renders must set `platform`. What hangs off it:

- `prometheus.url` defaults to Thanos Querier on OpenShift and empty elsewhere; the value is `null` so an explicit `""` still means "off".
- OpenShift-only objects aren't rendered elsewhere: the service-ca ConfigMap (the watcher's mount of it is already optional), the `system:image-puller` RoleBinding, and the `Image` ClusterRole and its bindings. `cluster-monitoring-view` is bound only on OpenShift. `build.enabled` fails the render.
- The justfile's `AIBOM_PLATFORM=kubernetes` swaps `oc` for `kubectl` and empties the `system:admin` impersonation (`--as=`/`--kube-as-user=` with an empty value is the flags' own default, i.e. no impersonation).

## Deploy Versioning (`--version`)

`--version` is the single source of truth for what `just deploy` builds and how it's labeled: it sets the BuildConfig output ImageStreamTag, the Deployment's image reference, and (unless it's `latest`) `build.gitRef` — so the BuildConfig actually checks out and builds that exact commit, instead of always building whatever `build.gitRef`'s branch currently points to regardless of the tag name.

Defaults to the short SHA `scripts/remote-build-sha.sh` resolves (the remote tip of `build.gitRepo`/`build.gitRef`, read straight out of `charts/aibom-webhook/values.yaml` rather than a second hardcoded copy) via `git ls-remote`, not local `HEAD` — local `HEAD` can be ahead of, behind, or diverged from the remote (e.g. unpushed commits), and pinning `build.gitRef` to the resolved SHA also closes a race where the branch tip could otherwise move between resolving the tag and the build actually cloning it.

Each build lands on its own ImageStreamTag instead of overwriting a shared one, so `just deploy --version=<older-sha>` rolls back by rebuilding that exact historical commit rather than relabeling whatever's currently on the branch. `--version=latest` opts back into the old behavior: a mutable tag that always tracks `build.gitRef`'s branch tip. The resolved value also lands on the Deployment as the `app.kubernetes.io/version` label: `oc get deployment aibom-webhook -o jsonpath='{.metadata.labels.app\.kubernetes\.io/version}'` tells you exactly what's running.

`just deploy` doesn't rely on the BuildConfig's `ConfigChange` trigger, which (per OpenShift's own docs) only fires automatically the *first* time a BuildConfig is created, never on later edits like a new output tag — relying on it would silently leave the Deployment pointing at a tag nothing had built yet (`ImagePullBackOff`) on every deploy after the first. On a brand-new namespace, `deploy` detects the first install (`helm status` finds no existing release) and waits on that auto-triggered build instead of also starting its own, to avoid doubling the build time on that first deploy. Either way, expect a brief `ErrImagePull`/`ImagePullBackOff` on the pod while the build catches up to the Deployment's image reference — it resolves on its own once the image is pushed.
